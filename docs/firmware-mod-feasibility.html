Firmware modification: feasibility (GR IIIx 1.60)

Question: could a modified firmware, for example one that adds a recipe list to in-camera RAW development, be installed on a GR IIIx, and what happens if it fails? All of this is offline analysis of fwdc243b.bin 1.60. Nothing was flashed.

Labels: Read (from the code), Structural (from names and strings), Inferred (interpreted). Addresses are RTOS virtual addresses.

Short answer

  • Installing: the camera checks an update file with a checksum only. There is no cryptographic signature. A modified firmware with a correct checksum and a version number of at least the installed one would be accepted (Read).
  • Recovery: there is no backup copy of the firmware. But the updater runs in its own start-up mode (MENU held at power-on), which does not start the shooting or playback screens. A mod that lives only in RAW development can therefore be undone by flashing stock firmware the normal way (§2.1).
  • A mod that breaks early start-up, the updater, card access or the power-chip link would still be permanent. Such code must not be touched.

1. How an update is found and checked

1.1 Files on the card (Read, 0x5362aa3c, 0x5362ab1c)

File in card root Role (from the log strings at 0x5362887c)
FWDC<n>B.BIN User update (the file Ricoh publishes)
KB<n>.BIN, KB<n>CPU.BIN, KB<n>FLD.BIN, KB<n>FLL.BIN Factory updates: DSP, CPU, DSP+CPU, "full" variants
FWBYPASS "bypass update mode": the update is skipped
FWDEL.BIN Delete the update file after updating
NOWAIT, NOOFF.BIN, KBCHG.BIN Factory flags (meaning not decoded)

The updater also has a sub-CPU path (CpuFwUpdate, "to cpu : fw update request"), so the package can update a second processor as well as the main SoC (Structural).

1.2 Container checks (Read, FwDecoder, 0x5362bd44)

The update file has a 0x80-byte header and a 0x18-byte footer at the end. The checks, in order:

Check Error string
Header +0x30 equals the camera's project number (0x261) "project number is different!"
Header +0x78 equals the project number in both halves (0x02610261) "header project number is different!"
Header +0x7c equals 0xA55A5AA5 "header chek data is invalid!"
Footer +0x00 equals header +0x78 "footer project number is different!"
Footer +0x04 equals the same magic "footer chek data is invalid!"
Footer +0x08 (firmware type, 2 for a user update) is the expected type "footer fw type is different!"
The 32-bit little-endian words of the whole file sum to 0 (0x5362bcc8) "check sum is invalid!"

A second routine (0x5362bea8) applies the same sum-to-zero rule to a data block whose length is in its last word. For the 1.60 file, the whole-file sum is 0x00000000, so the last footer word is a balancing value (Read).

There is no hash, signature or key in this path. The RTOS contains no SHA-256, SHA-1 init, MD5, CRC-32 or AES tables. The one SHA-1 round constant found (0x536b4bf8) is inside an unrelated library routine with no route to the updater (Read for the absence in the updater; Inferred for the rest of the image).

1.3 Version rule (Read, 0x536284e4)

The updater computes (major << 16) + minor from the update file and compares it with the installed version. It accepts the file if the new value is greater than or equal to the installed one. Otherwise it logs "Update Version is older than Current Version!!".

Consequences:

  • A modified 1.60 that still says 1.60 is accepted on a 1.60 camera.
  • Stock 1.60 can be re-flashed over a modified 1.60, as long as the camera still boots far enough to run the updater.
  • Going back below 1.60 is not possible.

1.4 Battery

The update refuses to run on low battery ("update battery NG!", 0x53628408) (Read).

2. Where it is written and what that means for recovery

  • The package contains the boot parameter blocks (BOOTPARA, DRAMPARA), the RTOS, the Linux kernel, device trees and the Linux root file system (tools/segments.py) (Read).
  • The updater writes the eMMC boot area ("boot area write OK", "can't set emmc partition to boot 1!") and user partitions (FwPartition) (Structural).
  • No second firmware copy, no A/B bank selection and no "golden" image were found. The Bank strings belong to image buffers, not firmware (Structural).
  • The updater code itself is in the RTOS, which is part of what it replaces.

Inferred risk: if a modified RTOS crashes before the update check (early boot, card mount, UI start-up), the camera cannot reach its own updater again. The boot ROM of the SoC (Socionext Milbeaut SC2000A) may have a factory USB or serial boot mode, but no evidence for one is in the firmware, and its protocol is not known. Treat such a crash as needing a factory repair.

2.1 Update start-up mode: the built-in rescue path (Read)

At power-on the power-management chip reports a start-up reason. The RTOS dispatcher at 0x53229134 reads it from the message (+4, values 0–6) and logs one of "Startup : Normal", "Playback", "ModeSet", "BLE", "Version" or "Update". Ricoh's instructions trigger Update by holding MENU while switching on. The camera then asks "Update the camera firmware?" and runs the updater (m_factor == Factor_FwUpdate).

Update mode still starts the RTOS core, card access and a small dialog, but not the shooting screens or playback (Inferred from the separate start-up branch). So stock firmware can be flashed back over a mod as long as the mod changes none of:

  • start-up code, the start-up dispatcher, or the link to the power chip;
  • SD/FAT access and the updater (0x53627800–0x5362d800);
  • the UI framework the update dialog uses;
  • saved settings in a way that crashes start-up. Recipe values must stay inside the camera's own limits.

2.2 Guard (tools/patch_guard.py)

gr_repack.py runs this check and refuses to write a file that fails it. It is an allow-list. A change passes only if:

  1. it lies in the RTOS block (the checksum compensation word of §4.2, itself in the RTOS, is the only exemption; the payload's last word may not change);
  2. it is not in a protected range: the RTOS entry, the updater (0x53627800–0x5362d800) or start-up control (0x53228800–0x53229800);
  3. code changes lie inside one of the eight RAW-development source files, and data changes are referenced only by functions in those files. Data with no visible user is rejected.

A source file's extent runs from the first to the last function that references its assert file name. The compiler keeps a file's functions together:

Why an allow-list: a first version protected everything the Update path can reach through direct calls. Depending on how leaf functions without a prologue were counted, that gave 864 or 15,924 protected functions. Virtual calls and message dispatch are not visible to it, so it could not be trusted in either direction.

Limit: a change inside the allowed files can still crash the camera when RAW development is opened. That case is covered by the rescue path in §2.1; the guard only keeps changes away from the code that path needs.

3. What a recipe mod would need

  1. A correct re-packer (offline): encode a modified payload back into the container format. The format has literal frames (0x8000 flag in the frame prefix), so compression is optional. Fix the footer and the balancing word. First test: rebuild the unmodified 1.60 payload and check offline that it passes every rule in §1.2.
  2. Find the settings: the image-control model used by RAW development (ImageControlModel::Mode_RawDevelopment, RawDevelopmentImageControlDetailSetController, UserData::ImageControl_*, ActiveImageControlSet_No1/No2) and the structure that holds Custom 1/2.
  3. Smallest useful change: in the RAW development screen, a key loads the next recipe from a file on the card into the current image-control values, and the camera's existing preview redraws. This uses the existing FAT file code and the existing preview, and runs only after boot.
  4. Never touch: boot parameters, the boot area, the updater, start-up code, calibration ("AdjustData") or anything that runs before the UI is up.

4. Results so far

4.1 Payload layout (Read)

The decoded payload is a chain of blocks. Each block has an 8-byte name, a 16-bit type, a 16-bit index and a 32-bit size, followed by the data:

Offset Block Size Content
0x0 BOOTPARA 0x48 Boot parameters
0x58 DRAMPARA 0x22c DRAM set-up
0x294 PARTPARA 0x204 eMMC partition table
0x4a8 M0 0xae60 Code for a Cortex-M0 helper core (Inferred)
0xb318 BOOT 0x5538 Boot loader: loads RTOS, SRIC, shell list, adjustment data, Linux
0x10860 RTOS 0x10b55c0 Main system
0x10c5e30 LINUX 0x2ebc00 Linux kernel
0x13b1a40 INITFS 0xd41800 Linux initramfs
0x20f3250 SRIC 0xc000 Sub-processor code
0x20ff260 CPU 0x20000 Sub-CPU firmware
0x211f270 SHELLCMD 0x9240 Engineering command list
0x21284c0 ICONBIN 0x1181314 UI graphics
0x32a97e4 FDRVPARA, RES Parameters and resources up to the end

The blocks carry no checksums of their own. The only payload rule is that its 32-bit words sum to 0; in the official file the last word balances it (Read).

The boot loader's strings only report load failures ("RTOS FIRMWARE CODE load error!!", "RTOS START!"). It has no verify step and no recovery path, which confirms §2 (Structural).

4.2 Re-packer (tools/gr_repack.py)

The tool rebuilds a container from a payload of the same length and keeps the official frame layout: every frame stays at its place with its output size. Unchanged frames are copied byte for byte. A frame that produces changed bytes, or whose back-references now reach them, becomes a stored frame of exactly 0x6000 bytes (prefix E0 00). This is the only stored form in the official 1.60 file, which has 729 of them. Affected frames are found by decoding the result again. The first frame (0x8000 bytes) and the last, partial frame cannot be stored that way, so edits there are refused. This follows the method of GR Mod's container code (no code copied); see gr3x-vs-gr4 §1.1. Until 2026-10-15 the tool wrote merged literal frames of up to 0x7FFF bytes instead; no such file was ever flashed.

The payload's word sum is restored with a compensation word, not the last word, so the last word and every block's word sum stay official. The word is VA 0x53dc22e8 (payload 0xdd2b58): the bytes "Para" of the text MakeParameter at 0x53dc22e4. Its only reference is the movw/movt pair 0x536e9bdc/0x536e9c08 (11 instructions apart; searched without a distance limit, and no literal word points into the string), which passes it as the function name to the assert routine 0x536b93d0 (7,633 callers; arguments: condition, expression, file, line, function) for src/R2Y/ToneControlTuning.cpp. The text is shown only when that assert fails (Read). GR Mod uses the same text's word on the GR IV. A payload that changes this word itself is refused.

The tool then fixes the footer, re-runs every check from §1.2 plus layout checks (header, frame layout, each frame official or a full stored frame, first and last frame official, payload last word and block sums unchanged), runs the guard and decodes the result again.

Test Result
Unmodified 1.60 payload All checks pass; output is byte-identical to Ricoh's file
Balanced +1/−1 edit of two code words at 0x53188900 (test only, deleted afterwards) All checks pass; one frame stored; output is byte-identical to GR Mod's build of the same payload
Unbalanced +1 edit at 0x53188900 (test only) All checks pass; decoded payload differs in that word and the compensation word only; GR Mod's 34 container and self-checks pass (with its model-record check allowing zero records)
Edit in the first or last frame, or of the compensation word Refused
One log string changed in the RTOS (test only, deleted afterwards; earlier literal-frame version) All checks pass; decoded payload differs only in that string and the balancing word; file 41 KB larger

4.3 Where recipes live (Read, from the settings name list at 0xb5f488)

The camera keeps its settings in a numbered table whose names are stored as one comma-separated string (1044 entries). The image-control part:

Index Entry Meaning
99 StillActiveImageControlSet Which set is active: No0 (normal), No1 or No2 (Custom 1/2)
100–102 StillImageControlNo0 … No2 Image control chosen in each set
103–203 StillImageControlNo0Param<Control><Parameter> Fine parameters of the normal set, per control
204–304 StillImageControlNo1Param… The same for Custom 1 (Custom 2 follows)
882+ StillFwupImageControlNo1ParamCrossProcess…, …NegativeFilm… Controls added by later firmware updates

Parameters per control: saturation, hue, key, contrast, highlight and shadow contrast, sharpness, toning, filter effect, shading, clarity, grain (Particle) and HDR strength.

RAW development keeps no saved settings of its own (only PlayRawDevelopmentJpegSize). It works on a copy: RawDevelopmentModel (Model/RawDevelopmentModel.cpp, 0x5327b884…), with ConvertToRawDevelopmentModelImageControl (0x53288d64, maps the 12 image controls to the model's numbering), StartRawDevelopment (0x534a3994), PreviewRawDevelopment (0x534a3aa8) and ExecuteRawDevelopment (0x534a48a8). The shared ImageControlModel (51 functions, 0x532bd620–0x532c9bb0) has a RAW-development mode. The screens are RawDevelopmentParameterSetController and RawDevelopmentImageControlDetailSetController.

4.4 RAW-development parameter model (Read)

RawDevelopmentModel holds the working values while a RAW file is developed:

  • +0x82: active set s (normal, Custom 1, Custom 2);
  • +0x83 + s: image control of that set, numbered as in the table below;
  • parameter k of control c in set s: one byte at +0x86 + s·221 + c·17 + k (13 controls × 17 slots = 221 bytes per set);
  • if no control is set, values come from a second structure at [+0x24] + 0x77d + k (probably the settings recorded in the RAW file; Inferred).

4.5 Room for new code (open)

A recipe loader needs roughly 0.5–1.5 KB of new code. Results so far:

  • Padding inside the allowed files: 16 bytes in total. Not enough.
  • "Unreferenced" functions inside the allowed files: 50 functions (10 KB) have no direct call, pointer or movw/movt reference. But ConvertToRawDevelopmentModelImageControl is among them, and RAW development clearly needs it. So "unreferenced" does not prove "unused", and overwriting such a function is not provably safe.
  • Large zero runs in the RTOS: two in the code area next to the RTOS entry (0x53000d50, 4.7 KB; 0x53002080, 8 KB), likely early-boot data or stacks, and many in the data area that may be live variables. None is usable without knowing the section layout.
  • Start-up caveat for the guard: code in the allowed files may also run at start-up (constructors, model registration). Changes must therefore go only into code that runs on a user action in RAW development, never into constructors or initialisation.

Candidate: repurpose a user-triggered feature inside the allowed files, for example the RAW-development zoom handler (RawDevelopmentZoomController.cpp, 0x53188884–0x53189274), so that its button loads the next recipe instead.

5. Risk summary

Risk Status
Camera rejects a modified file Unlikely if §1.2 is reproduced exactly (Read)
Bad file is rejected before anything is written Likely: checks run in FwDecoder before FwPartition writes (Structural; order not traced line by line)
Power loss or crash during writing Probably unrecoverable; use a full battery (Inferred)
Mod crashes in RAW development only Recoverable: MENU + power, flash stock 1.60 (§2.1)
Mod breaks start-up, card access or the updater No recovery path found; factory repair (Inferred)
Undoing a working mod Re-flash stock 1.60 or later (Read, §1.3)
Ricoh update 1.61+ Replaces the mod; it would have to be redone (Read, §1.3)
Warranty Void (Inferred)

6. Still open

  • The exact order of decode, check and write in BothFwUpdate/FwPartition, to confirm that nothing is written before all checks pass.
  • What the boot loader in the eMMC boot area does on a bad RTOS ("BOOT VERIFY ERROR: Target:%02x" exists in the payload but has no code reference in the RTOS).
  • Whether the SC2000A boot ROM offers a USB recovery mode.
  • The meaning of NOWAIT, NOOFF.BIN and KBCHG.BIN.
  • The field layout of RawDevelopmentModel and the setter the detail screen calls when a parameter changes. This is the hook for loading a recipe.
  • Header fields +0x34 (0x1329a) and +0x54 (0x438ff331): not read by FwDecoder, kept unchanged by the re-packer.
