GR IIIx contrast-AF search: state machine outline

Offline decode of the per-frame contrast-AF step (0x53404b24, 957 instructions) in GR IIIx 1.60. It was read to answer one question: what happens between the phase-guided jump and the peak fit, and where would a shorter confirmation fit (af-subsystem §10.5, lever 1)?

This is an outline, not a full decode. Labels: Read (from the instructions), Inferred (interpreted), Unresolved. Field names in +0x… come from the debug writer (af-subsystem §4.8) where one exists; the rest are my own tags. No timings were measured.

1. Interface (Read)

0x53404b24(obj, uint8_t *dir, uint16_t *out) runs once per frame. It reads and writes fields of a large state object obj (offsets from obj):

Field Meaning
*dir Scan direction, 0 or 1. Flipped by eor #1 on each reversal.
*out Action code returned to the caller (section 2).
+0x4388 Mode word, compared with 2 and 4, and with 6…9 in one test.
+0xf7c Signed area or status index. −2 means "range exceeded" and −3 "end point" (Inferred), both consumed at 0x53404f38.
+0xc4ca [ContrastAfSearchPath], values 0, 1, 2 (section 3).
+0x14bd6 Reversal counter, capped at 2.
+0x14e88 Guide mode. 3 selects the 300·N µm margin of af-subsystem §5.5.
+0x14b9c [ElegantQuickSearch] flag.
+0xc468, +0xc469 Run flags. With +0xc469 set and +0xc468 clear the function returns code 4 at once.
+0xc4df Small guard counter, decremented once per call.

It calls helpers for the drive:

  • 0x533fe85c(obj, 1 or 2) starts a lens sweep in the given direction.
  • 0x533faadc(obj) is called before every hand-off. It is probably "stop lens and take the current position" (Inferred).
  • 0x533fac3c converts pulses to µm (af-subsystem §4.3).
  • 0x5340ba6c and 0x5340bc4c judge the contrast samples (section 4).

2. Action codes returned in *out (Inferred from the callers' context)

Code Set at Reading
4 function entry, 0x53404f48, 0x5340567c No action this frame, or search not running.
2 after 0x533fe85c (0x53404e5c, 0x5340553c, 0x53405600) A sweep was started or continued.
8 default at 0x53404c18; after a peak check at 0x53405000 Search is in progress, or a result was accepted (the accept case also sets +0xc470, +0x14ea6, calls 0x533fb3c0(obj, 2) and writes 2 to +0xfec).
0x20 0x53405170 End-point hand-off, after +0xc450 (FarEndPointState) is set to 1, 2 or 3.
0x40 0x53405138 Reverse and continue.
0x80 0x53405140 Give up (reversal cap reached, section 3).

I could not tie every code to its consumer, so treat this table as a hypothesis. The codes are clearly a bit set, not an enumeration.

3. Search path and reversals (Read, with Inferred labels)

+0xc4ca records how far the search has got:

  • Path 0: first pass. The lens sweeps in the direction the phase result suggested (or a default). The stop test compares the travel so far (GetLensDriveDistanceUm, 0x533fac3c) with |phase defocus| + margin (guided path 0x534051c8: margin 3 × 10 × x). When the travel exceeds it, +0xf7c is set to −2.
  • Path 1: after the first reversal (strb #1 at 0x5340539c, 0x53404e1c, 0x534055e8, 0x53405630). The direction bit is flipped and 0x533fe85c starts a sweep the other way. In the state-4 branch the margin 10 × 10 × x is scaled by 2, or by 3 when +0x14bd6 is non-zero (0x534052e0–0x534052ec; the exact meaning of that flag is Unresolved).
  • Path 2 (strb #2 at 0x5340576c): set after a comparison of two floats from 0x533f93c8 and 0x533f928c, together with a direction flip. What those floats are is Unresolved.
  • Cap. Each reversal increments +0x14bd6, clamped to 2 (0x53404e2c–0x53404e40, 0x53405504–0x53405518). At 2 the function returns code 0x80 (0x53405140).

So a failed guess costs one or two reversals, each a stop, a restart and the sweep back through the peak. This matches af-subsystem §5.5.

4. Sample handling and the peak check (partly resolved)

The sample detector (Read). The contrast-sample class (CafDetection, functions 0x5340bd24, 0x5340bdf0, 0x5340bf78) is fed once per frame with a raw contrast value and a lens position:

  • Both are smoothed with a [1 2 1]/4 filter over the last three values (0x5340bf78: (a + 2b + c) >> 2 for positions, and the same with 0.25 × (x + 2y + z) for the noise-normalised contrast of §4.4).
  • It keeps a sliding three-entry window of smoothed contrast and position. It counts consecutive rises (+0xbc) and consecutive falls (+0xbe), and resets the other counter on each change of direction. It also records the window's lowest and highest position (+0x60, +0x64) and two indices, +0x10 for the rising side and +0x14 for the falling side.
  • The raw history array (pointed to by +0x00) is written three entries at a time (0x5340c17c), so the entries after the newest sample are copies of it. This is how a five-sample window can be read at the newest sample.

The peak helpers (Read).

  • 0x5340ba6c(area) returns +0x10, minus one if the smoothed value at that index is above the one after it.
  • 0x5340bc4c(area, n) returns 1 when n ≤ 1. Otherwise it walks the five raw entries n−2 … n+2, carries a running maximum forward, counts steps where the next entry does not exceed it, and returns 1 if there is any. It therefore returns 0 only when all five entries are strictly rising. Because the entries after the newest sample are copies of it, that needs at least two real samples beyond n.
  • The peak fit (0x5340b4f8) works on five samples and returns early with fewer than two.

What the bc4c == 0 branch does (Read). The branch (0x53404fb8) sets +0xc470, calls 0x533fb3c0(obj, 2), writes 2 to +0xfec, clears +0x14e84 and sets the flag +0x14ea6:

  • 0x533fb3c0 builds a result record for every AF area and hands it to the result consumer (0x533ef0d8) with mode 1 or 2. Mode 2 is the one used here.
  • The only function that reads +0x14ea6 to act on it is 0x5340a5a0. When the flag is set it posts a completion event (0x533e7010, id 4, with +0xc470), sets +0xc460 and +0xfec, clears +0x14e84, and runs the final steps, ending in the debug writer 0x53409000.

So the branch is "the search has a result: publish it and finish". It is the success exit of the search (Inferred, from the completion event).

Still unresolved: why 0 means success. By my reading of the instructions, bc4c returns 0 only when five raw entries are strictly rising. A peak window does not look like that. Either the entries are not plain contrast (they may be a transformed or position-ordered series), or the array holds copies I have mis-indexed. I cannot say which. So the exact criterion, and so the minimum number of frames, is still not fixed by the code alone.

5. What this says about lever 1

  1. There is no separate "verify at the phase target" state. After the jump, the machine runs the ordinary search (path 0) from the target. The phase result changes the direction, the margin and the start point, not the confirmation procedure.
  2. Success needs samples on both sides of the peak (a five-sample fit and at least two real samples beyond the candidate, section 4). A confirmation shorter than that would be a new procedure, not a threshold change.
  3. Two independent costs can be attacked separately. The reversals (up to two, section 3) come from a wrong or missing direction. The five-sample minimum comes from the fit.
  4. A wrong guided direction is the expensive case. A correct one finishes on path 0. The direction comes from the phase sign. Better direction handling on weak but usable phase results would therefore save whole reversals, which is a bigger saving than trimming samples.

6. Open

  • What series bc4c tests, and so why 0 means success.
  • The meaning of every action code and where each is consumed.
  • The floats behind path 2 (0x533f93c8, 0x533f928c).
  • The tail of the function at 0x53405840, which sets +0x14b9a…9d and restarts a sweep.
  • The frame count from the jump to acceptance. First camera data (2026-10-29, af-debug-log check 5, 7 runs): contrast AF sampled at 200 fps (100 fps in one darker run) with 8-pulse steps. Six runs ended exactly 3 samples after the contrast peak, after 8–11 samples in all. One run went on 16 samples past its peak (21 in all). So the confirmation past the peak costs 3 frames, 15 ms at 200 fps; a controlled session should confirm this. Bright-edge session (9 more runs): the same, 3 samples (once 4) after the peak. The two long runs in 16 had no confirmed peak in AF area 0 but one in area 1, and swept 16 samples past it. So the stop test waits for area 0. Where that rule sits in this function or its callers is open.
