GR IIIx autofocus: how it works

Firmware: GR IIIx 1.60 (fwdc243b.bin, version 1.60.11.17), analysed offline with tools/rtos_analysis.py (Capstone disassembly of the RTOS image). Nothing was run on or written to a camera.

Evidence labels

  • Read: I disassembled the function and the statement describes what the code does.
  • Structural: taken from class names, dependency assertions (m_X != NULL), function-name strings or log strings; the code itself was not read line by line.
  • Inferred: the role follows from names plus standard camera-AF practice.

Addresses are virtual addresses in the RTOS image (load base 0x53000000, file offset 0x10870 in the decoded payload). They are given so the work can be checked. They are not needed to understand the text.

1. Where AF runs

The Socionext Milbeaut SC2000A runs two systems (Structural, from the device tree):

Domain Role
RTOS Sensor readout, image pipeline, AE/AWB, all AF code, lens, stabilisation, UI
Linux (1 × Cortex-A7, 191 MiB) Wi-Fi, Bluetooth, USB/MTP, smartphone API; relays settings such as AF mode or area

The AF code is C++ (about 900 functions across 43 source files). It uses fixed-point integer maths for phase detection, NEON SIMD for the inner loops, and double-precision floating point for contrast AF and curve fitting (Read).

3. Phase-detection AF (Zaf): step by step

3.1 Data source

Phase-pixel values come from the image processor ("PPU PDSP") through CaptureZafInterface, not from the CPU reading the sensor (Structural). ZafWaveData stores them per block: StoreZafData, SetZafDataBuffer, ConvertZAfDataAddBuffer (pixel adding/binning), IsZafDefectBlock (blocks with defective phase pixels are skipped), GetAreaAutoAddress/GetSelectAddress (Structural).

The frame is divided into Zaf blocks. ZafDefine maps block IDs to Auto-area IDs and position IDs. ZafOperationConfig sets block positions for SELECT, FACE, LEFT_EYE and RIGHT_EYE (SetFaceBlockPositionX, SetZafBlockPositionInfo) (Structural). So face and eye AF works by moving which phase-detection blocks are evaluated.

3.2 Per-block pipeline (ZafOperationSequence, Read, 0x53425380)

For each block:

  1. Fetch the "A" (left-looking) and "B" (right-looking) signals and their lengths.
  2. Reject signals of fewer than 20 samples.
  3. Filter (3.4), check contrast (ZafContrast), correlate (3.5), grade (3.7), convert to defocus (3.8) and hand off to prediction (3.9).
  4. A configuration flag sets the correlation edge margin to 2 or 4 samples. That many samples are dropped at each end of the signal before correlating.

3.3 Level matching (CorrectWaveLevelGap, Read, 0x5341e6a0)

The A and B pixels see different amounts of light (shading). With the two signal levels La, Lb and a gap value g, every 16-bit sample of the brighter signal is scaled: x ← x − x·g / max(La, Lb). Negative results are clamped to 0 and trigger an assertion. ZafShadingAlgorithm supplies the per-lens-position shading data from factory calibration (ZAfShadingCorrect) (Structural).

3.4 Filtering (ZafFilter, Read, 0x5341e8b4, 0x5341e300)

Two NEON stages, each with four variants selected by a level k ∈ {0,1,2,3} (tap spacing s = 2^k):

Stage Kernel Code
Smoothing y[i] = (x[i] + 2·x[i+s] + x[i+2s]) / 2, i.e. [1 2 1] (edges: 2·x) 0x533e89d4 … 0x533e929c
Difference y[i] = x[i] − x[i+2s] + 32768, i.e. [1 0 −1] with an offset to stay unsigned (edges: 32768) 0x533e9864 … 0x533e9ce0

In firmware 1.60 only variant k = 0 ever runs (Read). The level is chosen by 0x5341c884, which is mov r0, #0; bx lr: it always returns 0. The k = 1…3 kernels (the vld2/vld4 ones) are dead code. The GR IV image has no such kernels (see gr3x-vs-gr4 §5.3), which fits.

Together these form a band-pass edge filter. Correlation therefore matches edges, not brightness. The wider spacings pick out coarser detail, which helps when the image is strongly defocused (Inferred for that purpose).

3.5 Correlation (ZafCorrelation, Read, main loop 0x5341ae00)

  • Up to 256 samples per signal. The edge margin (2 or 4 samples, see 3.2) is removed from each end.
  • The search runs over shifts from 0 up to a maximum, which is capped at half the signal length. Results are stored in a table of up to 62 entries. Negative shifts are handled by offsetting A rather than B.
  • Metric (0x533e81c8, NEON): for each 8-sample block vabd.u16 computes |A−B|. The code then accumulates SAD (sum of absolute differences) and, in parallel, SSD (sum of their squares). A lane-mask table handles the last partial block.
  • Minimum detection (0x533e836c, 0x533e8390): a sliding 3-value window. The middle value is a minimum if it is not greater than either neighbour and the three are not all equal.
  • Multiple minima: every minimum found increments a counter. More than one sets a flag, which marks repetitive patterns such as fences or tiles where phase detection is ambiguous.

3.6 Verification pass (0x5341a650, Read)

If enabled for the mode, SAD is recomputed at the five shifts around the minimum (±2) on a second data set of the same block. The local-minimum test is repeated at min−1, min and min+1, so a minimum that doesn't reproduce is discarded.

3.7 Noise floor, "H0" (0x5341a8b4, Read)

Before grading, the code estimates how much SAD is plain sensor noise at perfect alignment. The firmware calls this H0 (hence the CalcH0 string): H0 = C × h0Bias / m_OverlapContrastBase.ave.

  • C is the overlap contrast of the signals.

  • h0Bias is halved when the contrast is below a configured threshold.

  • If the average is 0, the code logs m_OverlapContrastBase.ave:0 h0Bias:%d overlapContrast:%d (names from that warning string).

  • The graded error is SADmin − H0, clamped at 0.

  • If H0 is at least as large as the SAD step to the neighbouring shift, the "clear minimum" flag is cleared.

3.8 Reliability grading (0x5341a9d0, Read)

Everything is in 1/64 fixed point, normalised by the contrast C:

  • Normalised error E = 64·(SADmin − H0) / C
  • Valley depth D = 64·(SADneighbour − (SADmin − H0)) / C
Condition Result
E ≤ 64 (1.0) high reliability
E ≤ 128 (2.0) usable, provided D is deep enough
D ≤ 15 flagged as a shallow valley (low confidence)
relaxed modes limits 192 / 216 / 256 (3.0 / 3.375 / 4.0) apply

Candidate selection (0x5341ad78): candidates are compared by cross-multiplication (SAD₁·C₂ vs SAD₂·C₁), so the lowest contrast-normalised SAD wins. That makes blocks with strong texture and blocks with weak texture comparable.

3.8b Shift → defocus: the conversion factor (Read, ZafLensInfo)

The phase shift is turned into defocus with a factor K (0x53420a68):

K[i] = round( TSF[i] × correctionCoefficient )
correctionCoefficient = c0 + c1·e + c2·e²        (float polynomial)
e = EyeRelief [µm] = 1,024,000 / v               (0x534208f0; v from lens control)

  • TSF[i] (m_cnTsfTable) is a read-only table in the firmware: about 97 16-bit values in a geometric progression. It is not a per-block table, as an earlier version of this document said.

  • The index is the aperture in 1/8-stop steps (Av × 8). The evidence is Read, the conclusion Inferred but well supported:

    • ResetLensInfo (0x53420b60) clamps the index to 24…96. That is Av 3.0…12, i.e. f/2.8…f/64, and f/2.8 is the GR IIIx's widest aperture. Above 96 it asserts.
    • A sibling table read with the same index (0x53c1848c) halves exactly every 8 entries (682 → 341 → 170 → 85). That is ∝ 2^−Av = 1/N², which only works if 8 entries = 1 stop.
    • The firmware uses 1/8-stop units elsewhere too (ISO in 4.6).
    • ResetLensInfo also stores 79954 / K, plus two more values from per-aperture tables (0x53c18374, nearly constant at 110–112, and 0x53c1848c).

  • One firmware, two cameras (Read). The "GR IIIx" firmware file also contains full GR III support.

    • The build is project KB609 (build paths /mnt/d/dev/M10V/KB609/…; M10V is the Milbeaut chip).
    • At start-up SystemConfig reads a hardware ID. The value 0x24C (= 588) sets project type 1 (KB588); anything else is type 0 (KB609) (SystemConfig_GetProjectType, 0x536b4140).
    • SystemConfig_SetupProjectProperty (0x536b41d0) then selects a product record (filter flag, spec start year/month, name, tag). Project KB588 gets the GR III or GR III HDF record; KB609 gets the GR IIIx or GR IIIx HDF record. An ID from the adjustment data chooses the HDF variant: 0x1320E / 0x13216 for the III, 0x1329A / 0x1329C for the IIIx.
    Record (0x53d62…) Filter flag Since Name Tag
    …194 0 2019-01 GR III GR_III
    …1a8 1 2024-04 GR III HDF GR3_HDF
    …1fc 0 2021-01 GR IIIx GR_IIIX
    …124 1 2024-04 GR IIIx HDF GR3x_HDF

    So KB588 = GR III (28 mm lens) and KB609 = GR IIIx (40 mm lens). The filter flag is the HDF (built-in diffusion filter) marker, going by the adjacent SystemConfig_GetLensFilterType. The AF tables follow the project type, i.e. the lens:

    Camera TSF table Correction polynomial c(e)
    GR IIIx (KB609) 0x53c18f88: 28, 30, 32 … 12324, 13139 −0.15122 + 3.8743·10⁻⁵·e + 7.1339·10⁻¹⁰·e²
    GR III (KB588) 0x53c19058: 24, 26, 28 … 17232, 18466 −0.15295 + 3.6492·10⁻⁵·e + 1.1200·10⁻⁹·e²

    At the default e = 22,260 µm, c ≈ 1.06 (GR IIIx) or 1.21 (GR III); the squared term contributes about 0.35 and 0.55. HDF and non-HDF bodies of the same model share these AF tables.

  • EyeRelief is the lens's exit pupil distance. It is the optical quantity that sets the phase-detection baseline, which is why the factor must follow it.

  • If the lens reports v = 0, e defaults to 22,260 µm (22.3 mm).

  • A negative polynomial logs correctionCoefficient:%f EyeRelief:%d[um] and falls back to a constant.

  • K = 0 logs TSF:0 m_cnTsfTable[%d]:%d correctionCoefficient:%f and is forced to 1.

ZafPulse then expresses the defocus in motor pulses (Structural).

3.9 ZafPredictor: precise shift, not subject motion (Read)

Despite its name, this class predicts the exact (sub-sample) phase shift, not where a moving subject will be.

  • Driver (0x53426084): runs the correlation. If it finds several minima and none verified, it checks for a left/right level mismatch (0x5341e588). If there is one, it applies CorrectWaveLevelGap (3.3) and correlates again.

  • Sub-sample shift (0x53425ef4): from the SAD values S₋, S₀, S₊ around the integer minimum n, in 1/256-sample units:

    Variant Used when Formula
    Equiangular (V-line) fit (0x533e9ef0) the verification pass (3.6) succeeded n·256 ± 128·(S₋−S₊) / (max(S₋,S₊) − S₀)
    Parabolic fit (0x533e9f78, 64-bit) otherwise n·256 + 128·(S₊−S₋) / (2S₀ − S₊ − S₋)

    A centre offset of 128 >> level (from the filter level in 3.4) is removed. The result then passes a validity check (0x53425e20), which treats |shift| ≤ 11 as near focus.

  • Candidate list (0x53425dc0): for repetitive patterns, an interpolated shift is stored for every extra minimum (up to 50).

No subject-motion model was found in the phase-detection code.

4. Contrast AF (Caf)

This is where the floating-point work is: roughly 1,500 VFP instructions across the contrast units, compared with almost none in the phase-detection units (Read, counted; unit boundaries are approximate).

4.1 Lens position of a sample (CalcIntegralCenterPulse, Read, 0x533f979c)

The lens moves while the frame is being exposed. Each contrast value is therefore assigned the lens position at the middle of the sensor's integration (exposure) time. The code takes the positions at the start and end of the frame and a timing value (converted with an integer ÷1000), then interpolates linearly: p = p₀ + (p₁ − p₀) · t_center / T_frame. This avoids a systematic focus error when scanning quickly. T_frame is the sensor VSync period (lVsyncTimeUs); if it is 0 the code substitutes 4997 µs (200 fps) and logs a warning.

4.2 Peak fitting (CalcQuadraticCurve, Read, 0x5340ed10)

Three (position, contrast) samples around the maximum are fitted with a parabola y = ax² + bx + c in double precision, and the vertex −b / 2a is returned as the in-focus pulse position. Safeguards:

  • a zero determinant is replaced by DBL_EPSILON, with a warning;
  • |a| below a threshold (a flat curve) returns the middle sample;
  • a ≥ 0 (no maximum) also returns the middle sample.

4.3 Other Caf pieces

  • Units (GetLensDriveDistanceUm, Read, 0x533fac3c): µm = 1000 · pulses / m_wLensKfp. If the lens reports 0, it defaults to m_wLensKfp = 100 pulses per mm (10 µm per pulse) and logs a warning.
  • Diagnostics (Structural): the log line ZAF[%d] PEAK:%d LOG:%d(%d,%d,%d) AREA:%d/%d GAIN:%3.2f F:%d(AVE:%d) N:%d(AVE:%d) shows that contrast AF evaluates every Zaf block too. For each block it tracks peak position, recent samples, area, gain and running averages (F, N; possibly far/near).
  • Multi-area edge check (Structural): CheckCafMultiAfAreaEdgeV.
  • Wobbling (CafWobbling, Structural plus log strings): small lens oscillations for continuous AF and movie. It uses the same CalcQuadraticCurve. It has modes named Near, Middle, SuperLow, Joint Quick Return and Pint Shift. "Pint Shift" (pint = focus in Japanese camera jargon) is a per-direction pulse offset: [CAF] Set %s Dir PintShift %d[pulse]. It most likely compensates gear backlash (Inferred).
  • Sensor mode (log strings): [CAF] Set CIS DriveMode Fix CAF High / Fix LV. Contrast AF can force a faster sensor readout so more samples arrive per second.
  • Per-unit correction (Structural): CafIndividualLensCorrect. Macro: CafAfMacro.
  • AF window geometry (Read, 0x533ff16c with 0x533fd754): each AF window is computed from a grid of cells (horizontal × vertical counts). It is then widened by 4 % of its size on each side (0 % or 2 % in some grid modes), and the left and top edges are clamped at 0. This is window geometry, not a contrast margin.

4.4 Noise-normalised contrast (0x5340b3ac, Read)

Before contrast values are compared, they are corrected for sensor noise using per-readout-mode parameters. The row is chosen by the sensor drive mode, or row 5 when a flag is set:

Mode Table A (slope, offset) Table B (4 values)
0, 1 0.164, 0.040 370, 64, 4984, 2500
2 0.108, 0.350 386, 64, 15308, 9200
3 0.101, 0.380 567, 64, 25632, 14500
4 0.151, −0.081 532, 64, 15308, 7641
5 0.097, 0.014 532, 64, 15308, 4819

The exact formula (Read). The inputs are contrast C, brightness sum Y, number of pixels n (used as a = n/4), and gain g in Q13 fixed point. Table B's columns are B0…B3:

b      = Y / a                                   brightness per unit area
g'     = (g / 8192) / B1                         B1 = 64 → gain normaliser
offset = A.off + A.slope · √(b · g/8192)         √ = fdlibm sqrt (0x53153ba8 → 0x53155a90)
noise  = g' · a · 4·B3/B2 · log₂( g' · B0 / b )
result = ((C − noise) / a − offset) / b

So the columns act as: B0 a signal-level constant inside the log (370–567); B1 = 64 a gain normaliser; and B3/B2 the noise scale per readout mode. Calling B0 a black level and B2 a white level is Inferred.

The √(signal × gain) term is the classic shot-noise form, and the log₂ term scales with gain. Together they give a physically sensible noise floor that grows with brightness and ISO. The helper was identified as fdlibm's __ieee754_sqrt from its bit-by-bit loop: 22 iterations over the high word starting at r = 0x00200000, then 32 over the low word, plus the x·x + x inf/NaN path.

4.5 Wobbling peak estimate (0x53412110, Read)

For each AF area (a stride of 0x78 bytes per area), the wobble code fits a parabola through three (lens position, contrast) samples. The samples may be unevenly spaced, so it uses divided differences:

s₁ = (y₀ − y₋)/h₋ ,  s₂ = (y₀ − y₊)/h₊ ,  a = (s₂ − s₁)/(h₊ − h₋)
peak = x₀ + round( −0.5 · (s₂ − h₊·a) / a )   (sign adjusted for scan direction)
  • Spacings with |h| below a threshold are replaced by ±1.
  • If the curvature has the wrong sign (no maximum), the best of the three samples is used instead.
  • The peak position and peak contrast are stored per area.
  • Input is either the scan history or the latest wobble triple.
  • Duplicate lens positions are skipped when choosing the three samples.

4.5b Wobble control (Read)

The 920-instruction wobble driver (0x53414750) is mostly per-area array bookkeeping. The decisions sit in two helpers:

  • Step decision (0x534100dc), per AF area. It first computes a noise threshold T through the noise model in 4.4.

    • If |C_now − C_prev| ≤ T, it returns 3 (hold): the change is just noise.
    • If contrast fell, it reverses direction.
    • Otherwise it keeps the direction.

  • Contrast-history gate (0x534110e4). An area passes if its contrast per quarter area exceeds 2896, or if the max/min ratio of its recent contrast history exceeds 3.0.

  • Other tunables sit in a block at 0x53c16efc…0x53c16f58. Each is classified by how it is used (Read); none of them has a name in the firmware:

    Value Used in Role (from use)
    10 0x53413588, 0x53412418 history length: ring-buffer count and offset
    3, 3 0x53414750 confirmation counts: a state change needs ≥ 3 hits
    2.5 0x53414750 ratio test value > 2.5 × reference
    1.15, 2.99, 0.02, 0.008, 0.001 0x53413588 ratio thresholds and small tolerances in the history evaluation
    5 0x534112bc multiplier for a count limit
    10 (second) 0x534112bc multiplier on a per-area 16-bit value
    100 0x534112bc constant bias added to per-area weighted sums (Σ w·x + 100), a regulariser that keeps them away from zero
    0.6, 0.2 0x5340f7a8 initial per-area weights set at wobble start
    64.0 0x53412e44 low-contrast floor: contrast per quarter area must be ≥ 64 (and a counter ≤ 7) for a wobble check to proceed
    5 (u16 at …6f40) 0x53412d18 count threshold compared with a per-area counter
    6 or 3 (u16 at …6f54 / …6f1c) 0x53412b8c count limit, chosen by a flag
    0.012 0x5340f624, 0x53415674, 0x53415858 small threshold in wobble start and stop

Peak estimation for the wobble is the unevenly spaced parabola in 4.5.

4.6 ISO-dependent AF filter strength (PPU/AFDFTuning, Read, 0x536ede50)

The image processor's AF detection filter ("AFDF") is re-tuned by sensitivity:

  • The current gain, in 1/8-stop steps with ±0.0625 rounding, indexes a 1/3-stop ISO scale.
  • Each ISO band reads its own tuning byte.
  • Level 0/1/2 maps to register value 1/2/3; anything higher maps to 5.

So at higher ISO the hardware contrast filter is set differently, most likely smoother to fight noise (Inferred).

4.7 Scan stepping (Read)

The lens moves continuously while frames are being exposed, which is exactly why CalcIntegralCenterPulse (4.1) exists. The spacing between contrast samples is therefore motor speed × frame period, and the code also works with explicit step widths in motor pulses:

  • Base step width: CafStepWidth (field +0x43e6, named by the debug writer in 4.8) is set once at start-up and never changed. The start-up code stores the word 0x000D8000 at +0x43e4, so the half-word at +0x43e6 is 13 pulses. Neighbouring defaults: +0x43e2 = 21, +0x43da = +0x43de = 3.
  • Aperture-scaled step (0x533fc0c0): step = round( lensValue × √N × 0.06 × 4.8 ), with N = 2^(Av/2).
    • lensValue comes from lens control (0x533ec1b4); in one mode it is halved.
    • The step grows with √N: stopped down, the depth of focus is larger, so the scan can take bigger steps.
    • In motor mode 2 the step is instead a fixed 8 pulses, or a global override.
    • 0x533fc350 then adds this aperture term (× 8) to CafStepWidth.
  • Focus distance, not speed: motor parameters 0x5207/0x5227 return the current and target focus distance (Read, units Inferred). MotorControl (0x536f7bc4 / 0x536f7c34) takes the current position (+0x84) or the target position (+0x3bc), converts it with per-mode piecewise quadratic tables (0x536f7944), and multiplies by 1000.
    • The reverse conversion (0x536f7b58) divides by 1000, clamps against a near-limit table and returns pulses.
    • Out-of-range positions return error codes in the 0xE000000x range.
    • The firmware's CommonFocusPosMm naming suggests millimetres.
    • The callers' (1,000,000 + v/2) / v is therefore 1000 / distance in metres, i.e. an inverse distance (milli-dioptres). Focus position is close to linear in that. An earlier version of this document read it as a motor speed.
  • Absolute moves go through motor parameter 0x5924, the target position (5.2). One path moves to "stored position − 8" (0x53406a98), consistent with approaching from one side to take up backlash (Inferred).

5. How the camera decides between phase and contrast AF (Read)

Short answer: it doesn't switch between two separate systems. The phase-detection process never moves the lens itself. It measures and publishes a result, and the contrast-AF process uses that result to set up and steer its own move and search.

5.1 The arbiter only routes

AfArbitrate (member layout from its Initialize: +0x58 contrast, +0x5c other-AF, +0x60 phase, +0x50 lens control, +0x48 loop) is a mailbox task.

  • Its message handler dispatches on 32-bit message IDs.
  • Every broadcast helper (0x533e5ccc, 0x533e6084, 0x533e6980, 0x533e72d0, …) calls the same virtual method on all three processes in turn: contrast, then other-AF, then phase.
  • The only selector is GetAfProcessAddress (0x533e5d6c): index 0/1 → contrast, 2 → phase, 3 → other-AF.

No floating point and no reliability comparison happen here.

5.2 The phase process doesn't drive the lens; contrast AF jumps to its target

The dependency assertions make this explicit:

  • ZafProcess holds the arbiter, shared state, ZafControl, ZafDebug and ZafOperation, and no lens control.
  • OtherafProcess, CafWobbling and the factory/test path hold m_AfLensControl.

The phase side offers two entry points to the others (0x53426704, 0x53426aac): enable/disable phase detection, and request a fresh result.

Contrast AF does act on the phase result directly (Read). When it sets up an AF area (0x53406914 → 0x534007c4), it looks up the matching phase block (0x533fed24). If that block's reliability byte is ≤ 128, it calls 0x533ecb60, which:

  • writes motor parameter 0x5924 = param 0x5205 + defocus × param 0x8231 / 1000,
  • then reads back 1,000,000 / param 0x5227.

0x5924 is the focus target position (Read, by units and scaling):

  • Parameter 0x8231 is the lens's pulses per mm. It is the same value contrast AF stores as m_wLensKfp (0x533f68bc → 0x533ec1ac → 0x533ed100), and it turns µm into pulses in GetLensDriveDistanceUm.
  • So defocus [µm] × 0x8231 / 1000 is a distance in pulses, which means 0x5205 must be a position too: the current focus position.
  • MotorControl scales both the same way internally: the 0x5205 getter returns field +0x84 ÷ 2, and the 0x5924 setter stores value × 2 at +0x3bc.

So when a phase block is reliable, contrast AF sends the lens straight to the phase-detection target (current position + defocus in pulses). The contrast search then runs around that point within the phase-bounded range (5.5). The read-back 1e6 / param 0x5227 is the new target distance as an inverse distance (1000 / m), recorded for the contrast state (4.7).

5.3 How contrast AF reads phase results

HybridAfInfo is a thin facade. Its getters forward to ZafInformation, which copies a result snapshot out under a mutex: the full info (0xEC0 bytes) plus a per-block table (0x508 bytes). One getter marks the copy as consumed, another clears it (0x5341ed58, 0x5341ef08, 0x5341efb4).

Contrast AF then runs 0x533fd688:

  • If the snapshot is flagged invalid, every block entry is set to 0xFF (unusable), and contrast AF runs without guidance.
  • Otherwise each block's value is converted from 1/256 fixed point (v × 1000 / 256), and so is one overall value used as a distance tolerance (5.5).

5.4 Direction hint (0x533fd7c8)

Depending on a mode byte (1, 2 or 3), up to three phase candidates are checked. A candidate counts as usable when its reliability byte is ≤ 128.

  • Only one usable candidate: it decides the direction.
  • Two usable: their signed values are compared (≥ → direction 2, else 1).
  • Otherwise: the sign of the signed defocus values decides.
  • Nothing usable: the result is 0, meaning no hint.

The contrast scan starts in this direction.

5.5 Phase detection limits the contrast scan

  • Scan range (main contrast routine 0x53404b24): lens travel so far (GetLensDriveDistanceUm) is compared with |phase defocus| + margin. Once the travel exceeds that, the scan state is set to end or turn.
  • Margin formula (Read):
    • x = round(10 · 2^(Av/2)), which is 10 × the f-number when the input is the APEX aperture value (0x533fca84, stored at contrast field +0x43ac).
    • The debug writer names this field [CurrentFno10] (4.8), which confirms x = 10·N.
    • There are two margins, both in µm. They are added to |phase defocus|, which is in µm (5.3), and compared with GetLensDriveDistanceUm.
      • Path 0x534051c8: 3 × 10 × x = 300·N µm. The multiplier is state field +0x14e88, and this path is only taken when it equals 3. It is used after a phase-guided move. 0.84 mm at f/2.8, 1.68 mm at f/5.6.
      • Path 0x534052a0: 10 × 10 × x = 1000·N µm. 2.8 mm at f/2.8.
    • Growing linearly with N matches a depth-of-focus rule (depth ∝ N); that reading is Inferred.
  • Direction reversals: the scan reverses when sharpness falls. A counter caps this at 2 reversals (0x53405504–0x53405544).
  • Stop test (0x533faffc): the travel is compared with limits that include twice the overall phase-derived value, with a frame-count timeout as a fallback.
  • The peak is then fitted with the parabola from 4.2.

5.6 Re-triggering in continuous AF (0x53405e8c)

Each frame, a monitored value is compared with a stored reference as |log₂(current / reference)|. For brightness that is a change in stops. If the change is ≥ 0.1:

  • the reference is updated and a re-focus counter is incremented (at most 10 re-triggers);
  • a settling delay of round(fps × 5 / 30 + 0.5) + 1 frames is applied, which is about 6 frames at 30 fps;
  • in the relevant state, a fresh phase result is requested (0x533f1ac4).

The exact quantity being monitored is a ratio of two values the routine receives. That brightness is the physical meaning is Inferred.

5.7 Other components (Structural)

  • AfCyclic runs the per-frame loop and shuts down with a timeout (ShutdownTimeout).
  • AfPanDetect tracks release, movie-record and interrupt states.
  • Lens chain: AfLensControl → AfLensDrive → MotorOperationManager, with LensFmmCalc and the lens ROM data (LromCommunication, LensLromData). Calibration terms include FocusOffsetInfinite/Finite and the FocusShiftPulse* family.

6. Putting it together: one AF cycle

  1. AfCyclic ticks once per live-view frame.
  2. The image processor delivers phase-pixel data per block (CaptureZafInterface) and contrast statistics (StatAfInterface).
  3. For each selected block (area mode, face or eye position):
    • equalise the A/B levels;
    • apply the band-pass filter;
    • run the SAD correlation;
    • verify the minimum;
    • subtract the noise floor;
    • grade reliability;
    • convert the shift to defocus with the TSF table × exit-pupil correction (3.8b).
  4. The best block is the one with the lowest contrast-normalised SAD. Repetitive-pattern and shallow-valley flags lower confidence.
  5. AfArbitrate broadcasts the AF request to all three processes.
  6. Contrast AF pulls the phase snapshot:
    • For each AF area with a reliable phase block (reliability ≤ 128) it sets the focus target to current position + phase defocus (5.2), a direct jump.
    • It takes a start direction from the reliable candidates.
    • It limits its scan range to the phase defocus plus a margin: 300·N µm after a phase-guided move, 1000·N µm otherwise.
    • It samples sharpness, pairing each sample with the lens position at mid-exposure.
    • It reverses at most twice, and fits a parabola through the top three samples.
    • With no usable phase data it runs as plain contrast AF.
  7. The lens drives in pulses, with direction and aperture offsets and per-unit calibration applied.

7. What this means in practice

  • Phase detection needs edges across the phase-pixel direction and at least 20 samples. Low-contrast subjects fail the E ≤ 2.0 test and fall back to contrast AF, which is slower.
  • Repetitive patterns are detected (multiple minima) and handled cautiously, which is why focusing on fences, blinds or brickwork is slower.
  • Contrast AF accuracy relies on the parabola fit and the mid-exposure position correction, which is why it is precise but needs several frames.
  • On the GR IIIx, phase detection guides contrast AF rather than replacing it. A reliable result produces a direct jump to the phase target, and then the direction and a tight scan range (300·N µm). In the contrast path, the final position still comes from the contrast peak fit. That is consistent with precise focus and a short hunt around it. OtherafProcess never reads phase results.
  • The GR IV runs a closely related Zaf/Caf codebase (35 shared AF source files). The contrast-AF and wobble code is largely identical, but the phase side differs: reliability limits come from tables, there is one filter level, and new dead-zone and saturation handling exists (gr3x-vs-gr4 §5). Its faster AF may therefore come from hardware (sensor, lens, motor, a dedicated controller), from these phase changes, or from both. That cannot be separated offline.

8. Still open

All points listed as open in earlier versions are now resolved: the motor parameters (4.7, 5.2), the maths helper (4.4), the project codes (3.8b), the margin units (5.5), the scan steps (4.7) and the wobble constants (4.5b). What remains is detail rather than mechanism:

  • Small tolerances: 0.001–0.02 and the 1.15 / 2.99 ratios in 4.5b are classified by use, but not traced to individual decisions.
  • Distance units: "focus distance in mm" (4.7) rests on the ×1000 scaling and the …FocusPosMm naming. The motor parameter names themselves are not in the firmware.
  • Subject motion: a search of the AF code for predict/motion/velocity/ tracking strings found only backups of the phase predictor's sub-sample data (GetPredictorDataBackup, IsPredictorOkBackup). No subject-motion model was found; continuous AF re-triggers and wobbles instead (5.6, 4.5b).

These can be read with the same tools (tools/rtos_analysis.py: vtables_for, report, show).

9. Where the time goes

This section is derived from the code structure. No timings were measured, and none can be measured offline. It ranks where the design itself spends time, from most to least.

  1. The contrast confirmation, every time. In the contrast path the final position comes from a parabola fit through contrast samples (4.2, 4.5). A peak can only be fitted once there are samples on both sides of it, so the lens has to pass the best position and come back.

    • Direction-dependent offsets ("Pint Shift", "Joint Quick Return") add a return move to take up backlash.
    • The scan may reverse up to 2 times (5.5).

    Even a perfect phase result doesn't let the camera skip this. With a reliable result the lens jumps to the phase target (5.2), and then still searches a window of up to 300·N µm (0.84 mm at f/2.8) for the contrast peak. So it is the fixed cost of every AF cycle.

  2. Falling back to a blind contrast scan. Phase detection gives no usable hint when:

    • the signal has fewer than 20 samples (3.2);
    • the normalised error is above 2.0, or the valley is shallow (3.8);
    • there are several minima, as with repetitive patterns (3.5);
    • the snapshot is invalid (5.3).

    Then there is no jump, no direction hint, and the wider 1000·N µm margin (2.8 mm at f/2.8) or no bound at all. The scan may start the wrong way, which costs a reversal, and it searches until contrast rises and falls. Low light, low contrast and repetitive subjects all land here.

  3. Sampling is bound to the frame rate. Each contrast sample costs one frame. Because the lens moves continuously (4.7), speed and frame rate together set how finely the peak is sampled. The base step width is 13 pulses (4.7). With the fallback 100 pulses/mm that is 0.13 mm, so a 0.84 mm window would take roughly 6–7 steps per pass before the return move. The real pulses per mm comes from the lens, so this is an order-of-magnitude illustration, not a measurement. The firmware can switch the sensor to a faster readout for contrast AF ("CIS DriveMode Fix CAF High"). That shows the frame rate is a known bottleneck, and a mode switch itself costs time.

  4. Pull-based phase data. Contrast AF requests a phase update and copies a snapshot guarded by a mutex (5.3). Phase results are therefore at least one frame old when they are used.

  5. Continuous-AF settling and noise holds. After a 0.1-stop change, the code waits round(fps·5/30 + 0.5) + 1 frames, which is about 6 at 30 fps, and caps re-triggers at 10 (5.6). The wobble also holds whenever the contrast change is within the noise threshold (4.5b), which is more often the case in low light.

What this implies.

  • The largest single cost is structural: every AF cycle ends with a contrast confirmation, even when phase detection was reliable.
  • The second is how often phase detection fails its reliability gates.

Both are software policy. By contrast, frame rate and motor speed are hardware. That is consistent with the GR IV comparison: closely related AF code, so its improvements most likely come from hardware that makes both the phase data and the contrast sampling faster.

10. Software levers and practical implications

This section is an assessment derived from §§3–9. Nothing in it was measured, and it contains no instructions for modifying the camera.

10.1 Where the policy lives

The time an AF cycle takes is shaped by a handful of values compiled into the firmware:

Lever Value Section

10.2 Why none of them is an easy win

  • Each value is a tuned trade-off. Ricoh calibrated the AF per lens (TSF table per aperture, exit-pupil polynomial), per sensor readout mode (noise tables) and per ISO band (AFDF strength). The constants above sit inside that system; they are not stand-alone knobs.
  • Loosening the phase gates would put more scenes on the fast path. But the gates reject exactly the cases where phase detection gives wrong answers: low contrast, low light and repetitive patterns. The result would be "fast but sometimes wrong" instead of "slow but right".
  • Skipping the contrast confirmation after a reliable jump would save the most time (§9 item 1). But the phase result is the least precise stage: an integer shift, sub-sample interpolation, then a conversion factor that depends on the exit pupil. The contrast confirmation is what delivers critical sharpness at f/2.8.
  • Smaller windows or larger steps save frames, but risk passing the sharpness peak. A missed peak costs a reversal, which takes longer than the frames saved.
  • None of these values is a runtime setting. Changing any of them means a modified firmware image. That carries a risk of making the camera unusable, conflicts with Ricoh's no-downgrade policy, and depends on an update check that is not fully understood. It is outside this project's offline scope.
  • The hard limits are hardware: sensor frame rate, focus motor, and phase-pixel density. The GR IV runs closely related AF code (§7), which suggests part of its faster AF comes from there.

10.3 What an owner can do today

These tips are derived from the code paths and have not been tested.

  • Stay on the fast path. Place the AF area on a clear, well-lit, textured edge. Repetitive subjects such as fences, blinds, brick and tiles produce several correlation minima (§3.5) and push AF into the slow path. Very small or featureless areas can fall below 20 samples or fail the normalised-error test (§3.2, §3.8).
  • Low light. Keep the AF-assist lamp enabled. In low light, phase detection most often fails its gates and the camera falls back to a scan with no direction or range (§9 item 2).
  • Stopping down. The contrast window grows with the f-number (300·N µm), but so do the step (√N) and the depth of focus. The net effect on speed cannot be derived from the code, so this is an open question rather than advice.
  • Skipping AF entirely. Snap Focus and manual focus bypass the AF pipeline and remain the fastest option for street work.
  • Firmware. Official updates are the supported way AF behaviour changes: 1.10 improved low-light AF, 1.41 added Zone Select AF, and 1.60 is current.

10.4 Is the arithmetic a bottleneck? (Structural, no timings)

The question is whether the AF calculations themselves could be made faster to shorten AF. The code says the arithmetic is already cheap next to the things §9 lists.

Size of the work. Block IDs run 0…54 (0x5341c7e8: cmp r0, #0x36), so at most 55 Zaf blocks. Per block, the correlation makes one kernel call per shift (up to 62, §3.5). Each call handles 8 samples per loop pass with about 7 NEON instructions (0x533e8234), so up to 256 samples cost about 230 instructions. That is roughly 14,000 instructions per block and under one million per frame if every block were evaluated. A few milliseconds at most, against a frame time of about 33 ms at 30 fps. The clock of the core that runs the RTOS is not known, so this is an order of magnitude, not a measurement.

Already efficient:

  • The metric is NEON, integer, 16-bit. No floating point is involved.
  • The CPU has hardware udiv/sdiv (0x5313d850), so the divisions in grading and the sub-sample fits are single instructions.
  • Floating point (double) appears only in the contrast peak fit (4.2), once per fit.
  • Scratch setup per block is small: two 512-byte buffers and about 250 bytes of tables are cleared and copied.

Possible arithmetic savings (all Inferred, none measured):

  1. One kernel call per shift. Each call reloads the lane-mask, and reduces its accumulators to scalars. Processing several shifts per pass would reuse loads of the A signal. The gain applies to a stage that already takes a small share of a frame.
  2. SSD computed alongside SAD. Two of the four kernels accumulate the sum of squares in every call. I could not confirm where it is used.
  3. Dead filter levels. Removing them saves code size, not run time, because they never run.
  4. Every selected block is evaluated in full. Blocks whose contrast fails the early check could skip the shift loop. The code already rejects signals under 20 samples early.

Why this does not shorten AF. The time in §9 is lens travel, one frame per contrast sample, and the contrast confirmation. Making the phase arithmetic faster would only bring the phase result earlier within a frame; contrast AF still has to wait for the next frame and then move the lens. The phase-to-contrast handoff is also pull-based (5.3), so a phase result is one frame old when used. The arithmetic would matter only if the computation overran the frame time, and nothing in the code suggests that it does.

10.5 Which software changes would be felt (Inferred, no timings)

These are ranked by how much a user would notice, if a manufacturer changed policy in firmware. Nothing here was measured, and no lever can be applied without a modified firmware image, which is outside this project's scope. Arithmetic speed is not on the list (§10.4).

  1. Shorten the contrast confirmation after a top-grade phase result. Every cycle ends with a contrast scan and parabola fit (§9 item 1). The firmware grades a top tier already (E ≤ 1.0, adequate valley depth, reliability ≤ 128; §3.8, §5.4) but treats it like any reliable result. A small bracket around the phase target, without the reversal and backlash return, would remove the largest structural cost. Risk: the phase result depends on the exit-pupil polynomial and per-unit calibration (§3.8b), and depth of focus at f/2.8 is small, so the failure mode is back-focus.
  2. Drive continuous AF from the phase defocus. The re-trigger watches a ratio, which is brightness in the likely case (§5.6), and no subject-motion model exists (§8). Phase defocus is computed every frame. Re-focusing when its magnitude exceeds a threshold would keep the lens near focus, so a half-press would start close to the answer. This is probably the most noticeable change for AF-C.
  3. Keep repetitive scenes on the fast path. Several minima currently send AF to a blind scan (§3.5), although up to 50 interpolated candidate shifts are already stored (§3.9). Choosing the candidate nearest the current focus or the previous result would help fences, blinds and tiles.
  4. Keep phase detection alive in low light. Phase-pixel adding exists (ConvertZAfDataAddBuffer, CheckZAfDataAddDisable; §3.1). When it is enabled is not known. Enabling it earlier would raise the signal-to-noise ratio where the gates currently fail (§9 item 2).
  5. Cut dead time. About 6 frames of settling and a cap of 10 re-triggers (§5.6), phase data one frame old (§5.3), and one window and step for every reliable result (§5.5, §4.7). Each is a small saving.
  6. Skip avoidable backlash returns ("Pint Shift", "Joint Quick Return") when the last move already came from the compensated side.

Frame rate and motor speed are not software levers. Whether AF switches the sensor to a faster readout is not settled: the CIS DriveMode Fix code (0x5341768c) is a table lookup and does not show it.

Numbers for levers 1 and 2 are in §10.6.

10.6 Lever 1 and 2 in numbers (bounds, not measurements)

The firmware does not contain what is needed to compute an AF time in seconds. The frame rate during AF, the focus motor speed and the lens pulses per millimetre all come from the sensor drive mode and from per-unit lens ROM data (motor parameters 0x8231, 0x8237), not from the image. What the code does fix, and what follows from it:

Read from the code

  • The peak fit works on a window of five contrast samples (0x5340b4f8, which loads five values and hands them to the helper at 0x5340e40c; it is called from 0x53406914 and 0x53409000). It returns without a fit when it has fewer than two samples. So a contrast result needs at least 5 frames of sweep, and more if the peak is not centred.
  • The continuous-AF re-trigger compares |log₂(current/reference)| with 0.1 (0x53406320, literal 0.1), i.e. a ratio of 1.072 (7.2 %). The settling count is trunc(fps × 5 / 30 + 0.5) + 1 frames (0x53406340–0x53406378), which is 6, 11 and 21 frames at 30, 60 and 120 fps.

Imaging Resource measured the GR III (28 mm; same Zaf/Caf code family) at a full AF-S shutter lag of 0.175 s in Select AF (review; I could not fetch the page and rely on the search summary). The five-sample minimum alone is 167 ms at 30 fps, so a 30 fps AF sampling rate cannot fit that figure. Lever 1: shorter confirmation. With a 175 ms total and sampling at 60 fps, the five-sample fit is about 83 ms, roughly half of it. A three-sample bracket around the phase target would save 2 frames (about 33 ms at 60 fps, 17 ms at 120 fps) plus one reversal and one backlash return, whose motor time is unknown. Realistic range: tens of milliseconds, up to about half of a 0.175 s cycle if the reversal and return are also removed. That is the upper bound the firmware structure allows. It is a perceptible gain in sequences of shots, and near the threshold of notice for a single shot. The scan window is a stop condition, not a distance always travelled. Its size (300·N µm, 840 µm at f/2.8) against a depth of focus of roughly ±20–50 µm at f/2.8 (assuming a circle of confusion of 2 pixels to 1/1500 of the diagonal) means it is 15–40 times looser than the accuracy needed, so its size costs time only when the peak is not found.

Lever 2: phase-driven continuous AF.

  • Today: after a trigger the camera waits about 0.18–0.20 s, and the trigger is a brightness-ratio change of at least 7.2 %, not a focus error.
  • Phase-driven: a fresh phase result exists every frame (8–33 ms old), so a focus error can be acted on within 1–2 frames, about 0.15 s sooner per trigger, and, more usefully, it would fire on the quantity that matters.
  • What cannot be computed offline is how often the lens is out of focus at the moment of a half-press. That determines how much a user would feel.

Why Ricoh uses the live-view drive in AF-C is still unknown.

Dim light: how the contrast-AF frame rate is chosen (measured, 2026-10-29, all sessions). In AF-S the AF exposure time always equals the frame time (4,986 / 9,970 / 19,967 / 29,964 µs at 200 / 100 / 49 / 29 fps), and each frame rate is used until the AF gain reaches the same ceiling, about 524,288 raw (8× if 65,536 is 1×): the largest exposure (time × gain) seen at each rate matches frame time × 524,288 (2.56 / 5.24 / 9.83 / 15.71 against 2.61 / 5.23 / 10.47 / 15.72). So in dim light the camera trades frame rate, not gain. A higher AF gain ceiling would keep contrast AF at 100 fps longer (about 3× less time per sample) at the cost of a noisier contrast signal. Where AE makes this choice is not found yet: not in the contrast-AF code (the exposure arrives through 0x533fcac4, called by pointer), not a shell command (AE_Mode, AE_Store do other things; the AeCommandListener handlers SetContrastAfIso and SetContrastAfExposureManual, 0x53496250 and 0x53496178, have no shell route), and not a plain constant or a table of these frame times or line counts. Found since (Read + measured): contrast AF chooses the drive level itself. The byte at contrast-AF object +0x1022 is the level, 0 / 1 / 2 / 3 = 200 / 100 / 49 / 29 fps (snapshots: 0 in bright light, 3 in dim, 1 at times in between). AF posts message 0x67c40808 (0x533f728c) to LiveViewControl::OnMessage (0x5343787c), which calls SwitchLiveView(lv, 3, level, table) (0x53436184) with AF's per-level drive table (pointer at +0xfcc, on the heap; entries at +0x00/10/20/30/40, bytes at +0x50). The code that writes +0x1022 is not found by direct addressing; the next probe dumps the table and the AE exposure info (+0xfe8) to look for the thresholds.

Dim light: the frame rate is necessary (measured, 2026-10-29). Forcing contrast AF to 100 fps in dim light (a third of the light per sample) raised the share of sweeps that found no peak from 5% to 46% and of path-2 sweeps from 23% to 62% (af-debug-log). The slow drive levels are what make contrast AF work in the dark; neither a faster level nor a higher gain ceiling is a lever.

Why it needs that light (measured, 2026-10-29): the contrast measure has a sensor-noise floor that grows with √(brightness × gain), so dark frames flatten the focus peak; fast modes also read fewer lines. More pixels can stand in for light: every sweep with the wide AF area (178 instead of 90) found its peak (af-debug-log).

Dim light: phase confidence. In the AF-S dim session, sweeps with a low phase grade (0/0) took 467 ms median against 240 ms with grade 1/1, through more reversals. In the dim AF-C session, with one larger AF area (178 × 144 instead of two of 90 × 54), the grade was 1 in 17 of 18 sweeps (Inferred: the larger area gives phase detection more signal).
