AF debug log on the camera

Goal: get the per-run contrast-AF data that the firmware can write to the card (gr-mod-landscape §5.1), for the measurements in af-subsystem §10.6. GR IIIx 1.60 only. This procedure has not been run on a camera yet. The SD-script switch is tested by GRKit users; the AF command is not.

1. What this does

  • A one-time ModeSet command turns on the camera's SD-script setting. It stays on until a second ModeSet command turns it off (§7).
  • At each power-on, the camera runs SCRIPT/STARTUP.TTL from the card. Ours waits 3 s, then sends EnableAfDebugDataSave 1 C to the engineering shell, then asks Linux to write a marker file.
  • With the C flag set and a save armed by CAF_Debug SaveDebugFile on, contrast AF writes one CSV to the card root at the next AF start (named Caf_0000.csv, then CTmp0001.csv, CTmp0002.csv …: the camera shortens the long name). The save is one-shot, so the script re-arms it every 3 s, once the contrast AF object exists (CAF.OK, see §4).
  • Nothing is written to flash. The flag lives in RAM and is gone after power-off. Without the SCRIPT folder on the card, the camera behaves as stock (SD scripts on, but nothing to run).

2. Before you start

  1. Check the firmware version in the Setup menu: it must say 1.60. The ModeSet file name is per camera and firmware family; the one here is for the GR IIIx.
  2. Use a separate, empty card, formatted in the camera. Not the GRKit card (ours replaces SCRIPT/STARTUP.TTL), and no FWDC*.BIN on it (MENU at power-on is also the firmware update start).
  3. Charge the battery fully.
  4. Generate the files on the computer: 
    python3 tools/af_debug_card.py            # writes work/af-debug-card/{enable,log,disable}
    --flags CZ also turns on the phase-AF log. Start with C alone: each log needs about 10 MB of free camera memory, and with too little the camera skips the log without telling you.

3. Turn SD scripts on (once)

  1. Camera off. Copy the contents of work/af-debug-card/enable/ (00078490.609 and DEVELOP.MOD) to the card root.
  2. Insert the card. Hold MENU and switch on. The camera should show "Mode Set Command", then "Complete", and switch itself off.
  3. Delete 00078490.609 and DEVELOP.MOD from the card.

If the camera instead offers a firmware update, or shows nothing and starts normally, stop: the file name does not match this camera.

On a Mac: Finder and cp leave ._name AppleDouble files next to each copied file on an exFAT card, even with cp -X. Delete them before ejecting (dot_clean -m /Volumes/<card>, or remove the ._* files). GRKit had load failures with cards that macOS had copied to.

The enable files and the SCRIPT folder of §4 can go on the card together, as GRKit's own install does: after "Complete", the next normal power-on runs the script.

4. Install the log script

  1. Copy the SCRIPT folder from work/af-debug-card/log/ to the card root.
  2. Switch on normally (no MENU). Wait 15 s in shooting mode.
  3. Switch off and look at the card on the computer. SCRIPT/AFDBG/MARK.OK should exist, with a line like 12.34 EnableAfDebugDataSave 1 C sent. That proves the script ran past the AF command. It does not prove the command was accepted; only the CSV files prove that.
  4. The script then runs SCRIPT/AFDBG/MEM.SH every 5 s for 10 minutes. It runs MEMRD.BIN, a 320-byte static ARM program that the generator assembles. The program maps RTOS RAM 0x5506b000–0x5506cfff read-only from /dev/mem (with O_SYNC, as GRKit's dump tool does) and writes it to SCRIPT/AFDBG/MEM.BIN. MEM.ERR holds its exit status (0 done; 1 open, 2 map, 3 create, 4 write). That region holds the AF debug flags, the CSV counter and the log slots. python3 tools/af_debug_card.py --read-mem MEM.BIN decodes it. It shows whether the command set the C flag, whether a log was opened, and how many CSVs were written.

Session: drive-mode selector (2026-10-29)

One start: some AF-C presses (discarded), 12 AF-S runs, then 11 AF-C runs, with 13 snapshots of the selector inputs, one every 10 s (work/af-logs/selector/). The 80 CSVs of an earlier unlabelled start are kept apart in work/af-logs/unlabelled-1/.

  • +0xc44e is 1 exactly in the AF-C periods (snapshots M002–M005 and M009–M012) and 0 in AF-S (M006–M008). AF-C searches therefore start in the selector branch that ignores CisDriveModeFix.
  • In that branch +0xc484 decides. It was 2 in two AF-C snapshots, and the AF-C runs alternated strictly: all 6 moves to near at 200 fps (80–90 ms), all 5 moves to far at 59 fps (267–333 ms), at similar defocus (780–1,110 µm).
  • Code (Read): the search end 0x533f48d8 turns +0xc484 1 into 2 (0x533f49d8), so the following search runs in the live-view mode. 0x533f7390 sets it to 1 on a path with a 1,000 ms timer check; 0x533fb860 resets it to 0. The alternation in this session and the mostly-slow AF-C session (long holds) both fit this state machine (Inferred).
  • Two AF-S runs right after the warm-up AF-C ran at 100 fps on path 2 (32–35 samples); the other ten were normal 200 fps runs.

A patch candidate for a faster AF-C is therefore narrow: ignore +0xc484 = 2 in the selector's AF-C branch, or skip the 1 → 2 step at 0x533f49d8. Why the firmware switches some AF-C searches to the live-view mode (most likely to keep the display running) is not known, and only a camera test of a patched build could show the effect.

Dim-light gain-cap patch (prototype, 2026-10-29)

  • Change: the four gain caps in the drive table, about 8× → 24× (0x180000). Data in RAM, no code change. At 24× the 100 fps level reaches the exposure that the 29 fps level reaches today, so dim scenes should stay at 100 fps, with a third of the light per sample (a noisier contrast signal).
  • Patcher: GAINCAP.BIN (616 bytes). It checks the build identity, follows +0xfcc, requires the integration row 4,986 / 9,970 / 19,967 / 29,964 and a stock (or already patched) gain row, writes the row through /dev/mem with dsb and cacheflush, and reads it back. With an argument it restores the stock row. Exit in GAIN.ERR: on 0 done or already, 3 other build or no table yet, 5 unexpected table (nothing written).
  • Switch: SCRIPT/AFDBG/GAINCAP.ON. MEM.SH runs the patcher with every snapshot (2 s), because the table may not exist yet at boot or may be rebuilt.
  • Checked offline: in the emulator with the camera's real snapshot and table: apply, already applied, restore, restore when stock, unexpected table (exit 5), other build (exit 3).
  • First camera run (work/af-logs/gaincap-24x/): GAIN.ERR on 0, but no effect. The last table dump (taken before each patch run) showed the stock caps, no AF frame exceeded gain 525,312, and 10 of 17 sweeps still ran at 29 fps; the owner could not tell a difference. Either the camera rewrites the table between runs, or the write does not reach what the camera uses. The patcher now exits 6 for "already patched" and 0 only for "written now", and MEM.SH logs every run to GAIN.LOG to tell the two apart.
  • Second run, with the run log (work/af-logs/gaincap-log/): GAIN.LOG shows exit 5 ("unexpected table") in most runs, 0 (written) a few times and 6 (still patched 2 s later) once. The camera rewrites the table continuously. The last dump, in brighter light, read gain 25,746 / 12,857 / 8,200 / 8,200 and integration 4,986 / 9,970 / 15,658 / 15,658 µs: time × gain is the same at every level (about 128.4 M). So the table is AE's current exposure plan for each level, the same exposure split into integration (at most the frame time) and gain clamped between about 8,200 and about 524,288, not a table of limits. Patching it cannot work; the patch is switched off again.
  • The gain scale (Inferred): the minimum 8,200 is about 8,192 = 213 and the maximum 524,288 = 219 = 64× the minimum. With the minimum at ISO 100 (base ISO), the AF gain ceiling is exactly ISO 6400, a common Auto-ISO upper limit. If contrast AF takes its ceiling from that setting, raising the limit in the menu would raise the ceiling with no patch. Not tested yet. The clamp code itself was not found (0x80400, 0x80200 and 0x2008 do not appear as such in the AE code).
  • Auto-ISO limit test (work/af-logs/iso-102400/): with the Auto-ISO upper limit at 102400 instead of 6400, the AF gain still peaked at 525,312 (as in every session), 9 of 15 dim sweeps ran at 29 fps, and the table showed levels 0–2 at the ceiling. The ceiling does not follow the menu setting. The three 0x80000 uses in LiveViewProcess are event-flag masks, not a clamp.
  • Physics (Inferred): the per-sample noise of contrast AF is set by the light collected per sample. More gain at a shorter integration amplifies signal and noise alike, so 100 fps at 3× the gain gives each sample a third of the light (about 1.7× worse signal-to-noise). The ceiling (about 8×, the ISO-6400 equivalent) is probably the analog gain limit of this readout; beyond it only digital scaling would be possible, which adds no information. Slowing the frame rate in dim light is therefore most likely a deliberate noise trade-off, not an arbitrary limit.
  • Not known: whether the level choice reads this cap (if not, the patch only allows more gain without changing the frame rate), whether 24× is within what the sensor drive accepts, and whether contrast AF still finds the peak in the noisier signal.

Dim-light frame-rate test: force 100 fps (prototype, 2026-10-29)

Question: does contrast AF still find focus in dim light at 100 fps, with a third of the light per sample? (A higher gain ceiling would give the same light per sample, so this tests that idea too.)

  • Change: the five instructions that read the drive level (ldrb rX, [obj+0x1000, #0x22] at 0x533f2604, 0x533f728c, 0x533f8dc0, 0x533f8f14, 0x534057b8) become mov rX, #1, so contrast AF uses level 1 (100 fps) everywhere. Test only: it also slows bright light from 200 to 100 fps.
  • Patcher: FORCE100.BIN (568 bytes), a general multi-site patcher. It checks the build, checks every site before writing any (all stock: apply; all patched: exit 6; mixed or unknown: exit 5, nothing written), then writes, flushes and verifies each site. Any argument restores. Switch SCRIPT/AFDBG/FORCE100.ON; run once after boot by PATCH.SH; result in FORCE.ERR.
  • Checked offline: emulator over the 1.60 image: apply, already, mixed, unknown word, restore, other build.
  • Risks: a writer of the level we have not found might still act on the real level, and the AE plan for level 1 in dim light is underexposed (gain at the ceiling, 10 ms). AF may hunt or miss; the live view may look darker during AF. A power-off removes the patch.
  • Camera run (work/af-logs/force100/): FORCE.ERR on 0; all 13 sweeps ran at 100 fps. The owner saw focus fail far more often and the screen get darker during AF.

Why contrast AF needs light (analysis, 2026-10-29)

From all logged sweeps (tools/af_light.py; 340 unique sweeps over all sessions).

  • The contrast measure has a noise floor. Its lowest value in a sweep, per pixel, grows with √(brightness per pixel × gain): log-log slope 0.47 against 0.5 for pure sensor shot noise. So the floor is sensor noise passing the contrast filter, not scene detail. Brightness itself is steady (frame-to-frame jitter 0.1–0.5%); the contrast series jitters about 2–4% in every mode.
  • Dark frames flatten the peak. The focus peak has to rise above that floor. Sweeps that found no peak rose only 11–18% above their minimum (3–5 noise widths), against 25–110% (8–50 noise widths) for sweeps that did. The forced 100 fps frames were about 3× darker per pixel (median 41 against 120 at 29 fps) and the floor ate most of the rise.
  • Fast modes also read fewer lines. For the same 90-wide area the main AF area spans 18 / 38 / 54 / 88 readout lines at 200 / 100 / 49 / 29 fps, so a fast sample loses both exposure time and pixels. A signal budget N × (Y/px) / gain had a median of about 60,000 or more in stock sweeps (100 fps: 62,800, 90% found a peak) and 17,660 in the forced 100 fps sweeps (54%).
  • One calibrated noise model per sensor mode (algorithm columns CoafA … LinearSlope): 200 and 100 fps share one; 49, 29 and 59 fps (AF-C live view) each have their own. The peak threshold is 0.0023–0.0040 at 200/100 fps and 0.0018 at 29 fps (relative).
  • The wide AF area works. In AF-S the camera sometimes switches the main area from 90 to 178 wide (90 × 88 → 178 × 144 at 29 fps, 90 × 38 → 178 × 62 at 100 fps), always right after a sweep that reversed or failed, so apparently on a retry. All 21 such sweeps found their peak, some with a rise of only 6–10%, including both in the forced 100 fps session right after a failed narrow sweep. The logged size is a per-area table at CAF +0x4200 indexed by the main-area index +0xf7c (printed by 0x534091d4).

Correction, same day: the wide area is only a small lever. In the standard AF-S layout area 0 is narrow (90) and area 1 wide (178), both measured in every sweep (snapshots of the width table at CAF +0x4200; a retry widens area 0 too). Comparing the two areas within the same 168 sweeps (same light, same lens path), the wide area's peak-to-noise ratio is only 1.12× the narrow one (median; better in 102 of 168), not the √2 that twice the pixels would give, because its peak is flatter (e.g. rise 0.64 against 0.73 at 29 fps): the extra pixels are mostly background. In the failed forced-100 sweeps the wide area 1 found no peak either. So the 21 successful wide-area retries owe most of their success to being a second pass over a narrowed lens range, not to the width. Starting with the wide area would gain roughly the equivalent of 25% more light; not worth a patch.

Dim light: the first pass turns back (analysis, 2026-10-29)

  • Path 1 is a real reversal. Every store of path 1 (0x53404e1c, 0x5340539c, 0x534055e8, 0x53405630) comes with eor r8, r8, #1, a direction flip. The CSV sample table restarts at the turn, so it shows only the last pass; the first pass is not logged.
  • In dim light most sweeps reverse, even with a confident phase result (grade 1: 34 of 42 took path 1). In AF-S, when the first pass ends without an accepted peak, the code at 0x53404d8c calls 0x53400b74 and 0x53403808 (about 1,000 instructions, the end-of-pass decision) and, if that returns 0, reverses at 0x5340561c.
  • The first pass crosses the peak without accepting it. Corrected by the state trace below: in a clean reversal the first pass starts at or just past the peak and moves away from it; contrast falls from the first sample. The return pass retraces those samples before it reaches the peak, which is why the peak sits about 7.5 samples (median, IQR 6.6–12.5, 60 dim path-1 sweeps) into the logged pass.
  • Cost: measured directly in the trace below: a clean reversal adds about 320 ms (about 880 ms against about 560 ms from the half-press to the accepted peak).

Static decode so far (Read): the main peak check (0x53404f50, calling 0x5340bc4c) is reached only from 0x53404bd8, which requires the byte +0x14ea5 to be non-zero. Nothing in the AF code sets it; only the constructor and vtable slot 13 (0x533f5024, a reset) clear it. So peaks are apparently accepted at the end of a pass, in 0x53403808. The pass ends when the countdown +0xc4df reaches 0 (0x53404ba0), and its writer is not found by direct addressing either.

AF state tracer: TRACE.BIN (540 bytes) maps the static contrast AF object read-only and records 16 state words (action code, path, countdown, accepted and success flags, the gate byte, area index, sweep start, window end, in-focus pulse, reversal count, drive level, drive state, area-0 detector counts, far-end state) every 2 ms for 60 s, with a monotonic timestamp, appending to TRACE.DAT in chunks. Switch TRACE.ON; started in the background by PATCH.SH; decoded with tools/af_debug_card.py --read-trace. Checked in the emulator over a real snapshot.

  • The search starts about 6 samples before the expected peak. In clean runs the peak comes after 4–7 rising samples (45–53 pulses into the logged pass). In wrong-side runs the return pass rises 6–8 times: 4–5 of them retrace the first pass, so the scan start was 1–3 samples past the peak. The start error spreads over about ±3 samples in dim light; the phase grade was mostly 1 in both groups.
  • A turn costs about 10 samples: 4–5 falling samples until the turn, the same number again on the way back, plus about 40–70 ms for the turn itself (path 1 action 2 to 4).
  • The rise/fall detector has no noise margin (0x5340bf78–0x5340c178). It smooths the contrast series ([1 2 1]/4, plus a predicted next value [1 3]/4), and any smoothed sample below the previous one resets the rise count (+0xbc) and increments the fall count (+0xbe), and the other way round. In dim light noise breaks the run of rises, so the detector never sees enough rises then 3 falls in a row: those are the 1.5–2.7 s presses.
  • A clear rise is not always accepted: in run 1 the second pass rose 7 times and fell 10 times without action 8. The CSV shows only the last pass, so the contrast values of that pass are not known; the tracer would have to record them.
  • The gate byte +0x14ea5 stayed 0 throughout, as the static read predicted.

Tracer, second version: 13 more words for the rise/fall detectors of AF areas 0 and 1 (horizontal, at +0x102c + 0xc4 × area; the vertical ones are at +0x2724): raw contrast, brightness, the noise-normalised values b0, b4, b8 of the last three frames (computed by 0x5340b3ac from the per-mode noise model), the counts, and the area-0 peak margin factors (+0x4c, +0x80). The update counts a rise when (b4 + 3 b8)/4 > (b0 + 2 b4 + b8)/4, otherwise a fall. Records are 124 bytes. --trace-contrast prints one line per frame and area during searches; the decoders still read first-version traces.

Contrast trace, dim AF-S with low-contrast targets (2026-10-29)

work/af-logs/dim-contrast: tracer v2, 10 presses, several on dark low-contrast surfaces as asked. 5 accepted on the first pass (616–1,172 ms), 2 after a turn (about 1.8 s), 3 failed after three passes (2.8–3.9 s, action 64).

  • The failed passes are not lost in noise. In the rejected first and second passes of the failed presses (22.1 s, 22.8 s, 43.9 s, 44.7 s) the smoothed area-0 value ((b0 + 2 b4 + b8)/4) shows one clean peak: 4–6 rising frames, then 5–8 falling ones, a swing of 0.021–0.035, about 2–3 times the area-0 peak margin (+0x4c × +0x80) and well above the frame-to-frame jitter after the peak (about 0.001). The rise and fall counts reached the values that clean presses accept at.
  • Accepted peaks can be smaller: 0.010 (area 1, 50.6 s) and 0.021 (area 0, 11.8 s). So neither the size of the peak nor the noise decides; another test rejects these passes.
  • Candidate (static, not confirmed): after a pass, 0x5340467c sets the area index to −1 (no peak) when peak − minimum > 2 × (value at a given sample − minimum), with the values from the detector helpers 0x5340bbe0 (peak), 0x5340bc18 (value at the falling-side index) and 0x5340bc2c (value at a sample). Reconstructed from the trace, this ratio does not cleanly separate accepted from rejected passes, possibly because the trace sees the smoothing only every 2 ms and not the detector's own per-sample array.

What this means for patches: the overshoot idea (accept on the first pass) is wrong. Two levers remain. (1) The slowest presses: the contrast trace above shows that clear peaks are rejected by a test other than noise, so a noise margin alone would not help; that test has to be found first. (2) Wrong side: turn after fewer falling samples, or jump back to the first pass's start instead of retracing it; at most about 300 ms on about 4 of 10 presses. A wider start margin would cost about 100 ms on every press and save little on average.

AF-C fast-drive patch (prototype, 2026-10-29)

A one-word RAM patch, applied from the card at power-on. No GRKit and no firmware file; nothing goes to flash.

  • Change: 0x533f7118 in the selector's AF-C branch, movne r3, #1 (0x13a03001) → mov r3, #1 (0xe3a03001). AF-C searches then get the 200 fps CAF drive whatever +0xc484 says. The +0xc488 test and both vetoes stay.
  • Patcher: SCRIPT/AFDBG/AFCFAST.BIN (376 bytes, built by tools/af_debug_card.py). It checks the build identity (0x53002038 = 0x110b3c01, GR IIIx 1.60) and the stock word, writes one word through /dev/mem, then runs dsb and cacheflush and reads it back, as GRKit's installer does for its hooks. With an argument it restores the stock word. Exit status in PATCH.ERR: on 0 done, 3 other build, 5 unexpected word (nothing written), 1/2/4/7 open, map or read-back errors.
  • Switch: the start-up script runs PATCH.SH once after Linux is up. It patches only if SCRIPT/AFDBG/AFCFAST.ON exists. Without that file PATCH.ERR says off and the camera runs stock code. A power-off always removes the patch.
  • Checked offline: in an ARM emulator (Unicorn, syscalls faked over the decoded images): patches 1.60; leaves an already patched or stock site alone; restores; refuses GR III 2.10 and IIIx 1.70 (exit 3) and an unexpected word (exit 5).
  • Not known until a camera test: whether the RTOS core sees the new instruction at once (its instruction cache), and what AF-C does in the 200 fps drive: the live view may freeze or stutter during sweeps, which may be why Ricoh uses the live-view drive. If the camera misbehaves, switch off; without AFCFAST.ON or without the card it is stock.

5. Shooting sessions

Keep these fixed for all sessions: AF-S (except in the AF-C row), Select AF or Spot AF with the area in the centre, face/eye detection off, Full Press Snap off, a fixed focal length (no crop mode). Half-press only; you do not need to take pictures.

One power-on per condition. The file counter restarts at 0000 at every power-on, so a new session probably overwrites the last one's files. After each session, switch off and copy the CSVs into a folder named after the condition before the next one.

Each session:

  1. Switch on and wait 15 s.
  2. For each run: point at the far target (or infinity), then at the subject, and half-press until focus is confirmed. Release. 20 runs, at least 2 s apart, so that the script has re-armed the save (every second) before the next run.
  3. Then one extra half-press. The data of a run is probably written when the next AF starts, so this flushes run 20.
  4. Switch off. Copy every *.csv from the card root to work/af-logs/<condition>/. Delete them from the card. python3 tools/af_csv.py work/af-logs/<condition> prints one row per run and leaves out repeats and files without a search.

If the camera feels slow, freezes in a session, or no CSV appears, stop and note what happened (§8).

6. What to bring back

  • The work/af-logs/ folders, plus SCRIPT/AFDBG/MARK.OK.
  • A note per session: number of runs, anything unusual (a hunt, a failed AF).
  • Expected content of each CSV (from the label strings, not seen yet): lens position in mm and pulses, the phase search direction, phase defocus in µm, the loose-decision grade flag, an algorithm block, then per AF area the lens pulse and the horizontal, vertical and Y contrast of each sample. A parser comes after we see real files.

7. Turning it off

  • Stop logging: delete the SCRIPT folder from the card, or use another card.
  • Turn SD scripts off: copy the contents of work/af-debug-card/disable/ to the card root, hold MENU and switch on, wait for the camera to switch off, delete the two files.

8. If something goes wrong

From GRKit's recovery guide, which covers the same script mechanism:

  1. Camera hangs at start-up: try switching off. If it does not respond, take the battery out.
  2. Take the card out. Insert a charged battery and switch on without the card.
  3. Still no start: hold the playback button to start in playback; if the menu opens, reset the settings (this deletes your personal settings). Then switch on again without the card.
  4. Still nothing: stop and contact service. Do not push or pull the lens barrel.

A start-up hang caused by our script is unlikely: it only sends shell lines after a 3 s wait and writes one small file. The other risk is that writing a 10 MB CSV during shooting makes the camera slow or unstable; that is why the sessions are short and only the C flag is set.
