GR IIIx remote control: what Wi-Fi and USB can set

Question behind this document: can a computer or phone write a full image "recipe" (image control plus its fine parameters) to a GR IIIx without modified firmware? Firmware 1.60, Linux user space taken from the initramfs with tools/firmware/initramfs.py.

Labels as in the other documents: Read (from code or data), Structural (from names, strings and dependencies), Inferred (interpreted). Section 3.5 also records what a connected camera reported.

Short answer: no. Wi-Fi can switch between image controls, including Custom 1 and 2, and set WB mode and exposure. USB cannot write image settings at all. The only other channel is the factory adjustment interface, which is not meant for user settings.

1. Where the code lives

Path in initramfs Role
usr/bin/webapid Wi-Fi HTTP API (crow + rapidjson), webapi_server::*
usr/bin/mtpd USB MTP/PTP server (Android MTP plus Ricoh and Pentax code)
usr/lib/libcamera-controller.so camera_controller::*: the Linux-side client for the RTOS (IPCU)
usr/bin/camctld Camera-controller daemon

All three ELF files are stripped, but their C++ symbols are exported in .dynsym, so nm -D | c++filt names every function. (Read)

2. Wi-Fi API (webapid)

Endpoints (Read): GET /v1/ping, /v1/props, /v1/liveview, /v1/photos[...], /v1/transfers, /v1/changes (websocket), PUT /v1/params/camera|device|lens, POST /v1/camera/shoot[/cancel|/compose], POST /v1/lens/focus, POST /v1/device/finish, POST /v1/device/wlan/finish, GET /v1/debug/revisions.

Settable camera parameters (Read, from webapi_server::<name>::SetValue): av, tv, sv, xv, exposure_mode, metering_mode, focus_setting, effect, wb_mode, still_size, still_format, movie_size, shoot_mode, capture_mode, reso, operation_mode, datetime, geo_tagging, auto_resize, power_off_transfer, channel, ble_enable_condition.

effect value table (Read, static initializer at 0xe3680; the same table is used for still and movie):

Value String
0 off (Standard)
1 col_vivid
2–4 efc_monochrome, efc_softMonochrome, efc_hardMonochrome
5–9 efc_highContrast, efc_posiFilm, efc_bleachBypass, efc_retro, efc_HDRTone
10, 11 col_custom1, col_custom2

Negative Film and Cross Processing cannot be selected through the API.

wb_mode (Read, 0xed5a0): auto, multiAuto, daylight, shade, cloud, four fluorescent types, tungsten, incandescent, cte, colorTemp1–3, manual1–3, custom1–3. There is no WB shift value and no Kelvin value.

There are no keys for saturation, hue, key, contrast, shading, clarity, toning, grain or sharpness. (Read: no such strings or classes exist.)

3. USB (mtpd)

3.1 Name tables

The debug name tables are arrays of {const char *name; u32 code}. Reading them as {code, name} shifts every code by one entry. The standard codes expose this: for example 0xD407 is PerceivedDeviceType. (Read)

3.2 Vendor ("Pentax tether") operations (Read)

Code Name
0x9001 SET_PENTAX_VENDORMODE
0x9002 PENTAX_CAMERA_SHUTDOWN
0x900F GET_ALLCONDITIONS
0x9011 / 0x9012 INITIATE / TERMINATE_PENTAXCAPTURE
0x9006 GET_LIVEVIEWFRAMEDATA
0x9090–0x9095 GENERAL_PURPOSE_SET_VALUE, RUN_FUNC, END_CHECK, GET_VALUE, GET_DATA, SET_DATA

doSetPentaxVendorMode (0x503f4) needs an open session and more than four parameters. It passes parameter 3, which must be 0 or 1, to ChangeTetherMode(). The responses are 0x2019 (device busy) and 0x2002 (error). (Read)

3.3 Vendor properties (Read)

GetSupportedVendorDeviceProperties (0x67d70) lists these codes for the GR (the K-3 Mark III Monochrome has its own list): 0xD009 live-view area, D00F shutter speed, D013 drive mode, D014/D015 bracketing, D018 colour temperature, D01B file format, D01E ISO, D020 image tone, D021 saturation, D022 hue, D023 key, D024 filter effect, D025 monotone toning, D026 muted/bleach toning, D027 fine sharpness, D028/D029 contrast highlight/shadow, D02A composition adjustment, D02B focus assist, D02C cross process, D02D filter-effect user setting, D035–D039 live view and movie.

3.4 Image settings cannot be written over USB (Read)

  • DeviceProperty::SetDevicePropertyValue (0x68dd4) accepts only 0x5011 (date and time) and 0xD406. For anything else it logs "device prop not supported".
  • SetIpcuSaturation, SetIpcuHue, SetIpcuKey, SetIpcuContrast*, SetIpcuCustomImage, SetIpcuCrossProcessType, SetIpcu*Toning and SetIpcuWhiteBalance exist, but no bl calls them and no pointer refers to them. They are dead code shared with Pentax bodies.

3.5 Camera as connected (measured, 2026-10-14)

USB ID 0x25FB:0x2115, bcdDevice 0x0160, interface class 6 (still image), USB 2.0. gphoto2 --summary reports vendor extension "microsoft.com/DeviceServices" and only properties 5001, 5011, D406, D407 and D303, with no capture. No vendor command was sent.

4. The factory channel (0x9090–0x9095)

  • In mtpd, RicohCommand::doGeneralPurpose* pass their parameters through to CameraController::GetFactoryCommand() (FactoryCommandImpl::GPSetValue(data, len, u16, u16), GPGetData(u32, u32, …), GPRunFunc(u8, u8)). mtpd does no checks of its own. (Read)
  • On the RTOS side the commands reach HostCameraCommand::FactoryCommandServer and FactoryContentsControlService. Each service checks a category byte at command +0xaf8 and an item byte at +0xaf9. About 25 functions dispatch on the category: for example AF handles 0x15, 0x25 and 0x40 (0x533ebab8), and BE-still handles 2 and 3 (0x535250d4). (Read)
  • The services around it hold adjustment data: AWB gain, SR gyro and hall, ND filter, black level, defect pixels, Wi-Fi info. A "Factory Menu" also exists. (Structural)
  • No category for image-control or menu settings was found. (Inferred; not every dispatcher was decoded.)
  • Whether mtpd accepts these operations only in vendor mode was not checked.

Writing to this channel without a full map risks overwriting calibration data. It is not a route for recipes.

5. What a recipe manager can do on a GR IIIx

Route Full recipe?
Built-in RAW development (playback) Yes, but the parameters are entered by hand; only Custom 1/2 are stored
Wi-Fi API Switches image control (incl. Custom 1/2), WB mode and exposure
USB, standard or vendor mode No (§3.4)
USB factory channel Not usable for this (§4)
Modified firmware In principle; the update check and recovery are unknown

6. From inside the camera: USB and the HTTP API (measured, 2026-11-19)

An SD-card probe (tools/af/af_debug_card.py --probe, Linux side via lcmd) listed what the camera offers for a link to a computer. Evidence in work/af-logs/usb-probe2–4.

  • USB gadget: configfs gadget mtp on UDC 19c00000.dwc3, one function mtp.usb0. The kernel (4.4.15, /proc/config.gz) has only the MTP function (CONFIG_USB_F_MTP=m); ACM, ECM, NCM, RNDIS, EEM, mass storage and FunctionFS are all off. A second gadget cannot be created (ENOMEM).
  • Kernel modules: CONFIG_MODULES=y, no module signing, KALLSYMS_ALL, no STRICT_DEVMEM, modules_disabled = 0. A module built for this kernel could add a USB network function.
  • MTP view: the SD storage is "Camera layout (DCIM)": the stock mtpd shows only photos, not SCRIPT/.
  • USB and shooting: switched on with the cable attached, the camera first showed the USB screen (lens closed). After off and on it went to shooting mode with the UDC "configured", and the scripted AF presses worked.
  • busybox 1.24.1: nc, sort, tr and others are applets without a command link; call them as busybox nc etc.
  • webapid listens on 0.0.0.0:80 with Wi-Fi off and answers on 127.0.0.1: GET /v1/ping, GET /v1/props (all settings, focusSetting "spot" for the Select mode, focused, battery; also the Wi-Fi SSID and key, so the probe output stays local). POST /v1/lens/focus answers {"errCode":200,"captureId":n} and starts AF 40 ms later.

The API AF is the half-press AF. In the trace the call without a position ran exactly like the three scripted half-presses after it: pre-move, one sampling pass at 200 fps, lock (actions 8, 128), area 0, final position −16317 (the presses: −16309 to −16317), 260 ms. With pos=50,50 it used area 1, needed two passes at 100 fps and 492 ms, so a position selects another AF area.

Consequence: the card's Linux script can start AF itself through 127.0.0.1, and a computer on the camera's Wi-Fi can do the same. Arm switching and file access over the network need a small endpoint of our own on the Linux side (for example busybox httpd with CGI scripts).

7. Remote test controls for AF sessions (measured, 2026-11-19)

What a computer on the camera's Wi-Fi can change during an AF session, and whether it changes the light the AF sees (AF brightness Y and the margin scale of the contrast detector, one press each, same scene).

Shell relay (test card only). The remote card's startup script no longer ends after starting the endpoint. It loops: every 0.4 s it looks for SCRIPT/AFDBG/RELAY.TTL and includes it. The shell CGI (POST, 1 to 8 lines) writes that file: a sequence number, one sendln per line, and a call to RACK.SH, which writes the acknowledgement that status shows as relay_ack. A guard inside the file skips a sequence number the script has already run. Only commands in SHELL_ALLOW (tools/af/af_debug_card.py) pass, with arguments from [A-Za-z0-9 ._-]; the Mac checks the same list. The acknowledgement takes about 0.5 s. Client: tools/af/af_remote.py shell 'LINE' … and nd on|off. Once, the relay stopped after its second command, before a press and ND_open; after a power cycle the same sequence ran without a problem (cause unknown). Every call reports whether it was acknowledged.

Relay stalls and the pull relay (recipe card, 2026-11-22). The cause of those stops: Linux wrote RELAY.TTL (and its log lines) to the SD card while the RTOS read it. RECIPE.LOG shows six stalls over two days, each a batch that was never acknowledged, after which the heartbeat stopped too. The first three were written 0.45–0.50 s after the previous acknowledgement, which is when the loop reads the file next (11 batches in that window, 3 stalled; 85 outside it, none). Holding the Mac's writes out of that window cut the rate, but writes at other moments still met the loop's routine reads (seq 92, 23 and 67, 5.6–6.9 s after an acknowledgement). The recipe card (tools/recipes/recipe_card.py) therefore no longer lets Linux write the card on its own. The shell CGI only queues the batch in RAM (/tmp/recipewww/relay.next, busy while one is pending). Each round the loop runs lcmd sh /tmp/recipewww/PULL.SH, waits 400 ms, then includes the file. PULL.SH is the only writer of the card while the loop runs: the pending batch into RELAY.TTL (in place, 512 bytes), the log lines collected in RAM into RECIPE.LOG and ERR.LOG, then sync, and nothing at all when nothing is pending. RACK.SH and PULL.SH run from RAM, so lcmd does not read the card either. The AF remote card (af_debug_card.py) still has the old relay.

The engineering shell has 584 commands (a text table in the 1.60 image: name and handler address). The ones useful here, with the usage text each handler prints:

So the only remote dimmer is the ND filter, one step of about 1.7 stops; the lamp still sets the light level otherwise. The allowlist lives in the CGI on the RAM disk, so it can be widened over Wi-Fi without a card swap (an uploaded tool can rewrite /tmp/afwww/cgi-bin/shell until the next power-on).
