GR mod landscape and the AF work

Question behind this document: which community mod projects support the GR IIIx, and can one of them carry our autofocus work (af-subsystem, caf-search-state-machine)? Survey date 2026-10-29. Firmware: GR IIIx 1.60 (the camera in question), compared with GR III 2.10 and GR IIIx 1.70.

Labels as in the other documents: Read (from code or data), Structural (from names, strings and dependencies), Inferred (interpreted). Statements about other projects come from their repositories on the survey date. Those projects change daily (GRKit released 1.3.1 to 1.3.3 in two days).

1. Short answer

  • No project touches AF. All of them change image looks, aspect ratios, grain, date imprint, shutdown images or menus. Our AF analysis has no overlap with community work.
  • GRKit is the right base. It is MIT-licensed. It does not flash the camera: it patches the RTOS in RAM at every power-on from the SD card, and checks every site before it changes anything. Without the card the camera is stock.
  • AF cannot be a GRKit module. Modules may not name firmware addresses. AF needs a new core hook group in a GRKit fork, gated by a capability word that a small module page sets (§6).
  • The GR IIIx 1.60 RTOS is the GR III 2.10 RTOS. The decoded images differ in 45 words (model name, version, build date, a product table). The AF code is byte-identical, so our addresses are GRKit's pinned addresses (§4).
  • The camera has AF debug logging built in. The engineering shell command EnableAfDebugDataSave 1 C makes contrast AF write a per-run CSV of lens positions, phase defocus and every contrast sample to the card. A GRKit-style card script can send it. This may replace the 240 fps filming (§5).
  • Recipes no longer need a flash. The GR IIIx has the same UserData Set shell command that a GRKit fork uses on the GR IV to write Custom slots. It covers Custom 1 and 2 (103 names each). This supersedes the zoom-controller cave design (§7).

3. How GRKit works

From the GRKit sources (docs/architecture.md, docs/module-reference.md, crates/grkit-build, runtime/) at 1.3.3.

3.1 Loading

  • Enabling SD scripts is a one-time, persistent camera setting. Put DEVELOP.MOD and the camera's ModeSet file on the card (GR IIIx: 00078490.609, GR III: 00078350.588; corrected 2026-10-29, the GR III name was given here before), hold MENU while powering on, and the camera shows "Mode Set Command", then "Complete", and turns off. Our start-up dispatcher 0x53229134 logs "ModeSet" as its own start-up reason, next to "Update" (firmware-mod-feasibility §2.1). With those files on the card, MENU at power-on probably takes the ModeSet branch instead of the updater (Inferred, not traced).
  • At each power-on the RTOS script interpreter runs SCRIPT/STARTUP.TTL, which includes SCRIPT/GRKIT/LOADER.TTL. The script language looks like a Tera Term macro: sendln, filesearch, intdim, mpause.
  • sendln 'lcmd sh …' sends a line to the RTOS engineering shell. lcmd is the shell command (SHELLCMD table, 0x53014c90, Read) that runs a command on Linux. Linux then runs SCAN.SH and INSTALL.SH, which runs CORE.BIN --install. Only Linux can write the RTOS code region.
  • INSTALL links the modules, writes effects and icons, restores settings from GRKIT/STATE.TXT, and installs the hooks last. Private code lives in a reservation after the RTOS image. Data lives in script integer arrays (intdim), which the loader script allocates in the RTOS heap.

3.2 Hooks and relocation

  • A target pins one firmware build. The GR III family has one target, gr3-2.10 (crates/grkit-build/src/target/gr3_210.rs, runtime/targets/gr3-2.10.h), whose comment reads "GR III 2.10, which GR IIIx 1.60 also runs". GRKit's pinned firmware SHA-256 (d6a3c9c2…) and decoded SHA-256 (53da6907…) match ours.
  • A hook site is (symbol, address, stock bytes), for example ("grain_gate", 0x5351361c, "e7feffeb"). A hook spec says whether the site gets a B or a BL to the runtime code (components.rs).
  • Relocation (relocation.rs). For each address the build stores a window of masked words (16 before, 48 after) from the pinned image. The mask clears B/BL offsets, absolute RTOS addresses and MOVW/MOVT immediates. INSTALL searches each window within ±0x10000 of the pinned address in the running image. If a window is missing or found twice, it stops with status 47 and changes nothing. GRKIT/RELOC.BIN caches the results.
  • Hot paths never run module code. They read capability words (CORE.TONE, CORE.ASPECT, CORE.GRAIN, CORE.GRAIN_SIZE) that the menu sets.

3.3 What a module may do

A module (<ID>.GRM, C plus module.toml, ABI 2.0) gets settings, a choice page in ADJ and MENU, live-view layers (720×480 RGBA), plane filters on recorded YCbCr pictures, timers, toasts and dialogs. Callbacks run in the App task. The build rejects any undefined symbol that is not a listed service, so a module cannot call or patch firmware. Limits: 64 KB code per module, 1536-byte stack frames, no / or % on variables.

So an AF change is core work: a hook group in the family (target/gr3.rs), sites in the target, runtime code next to runtime/processing.S, and a new capability in crates/grkit-core/src/capabilities.rs. A module only supplies the menu page.

3.4 Safety

  • Nothing is written to flash. Removing the card, or deleting SCRIPT, gives the stock camera. An empty GRKIT/SAFE file stops all modules.
  • INSTALL.ERR records the step that was running. REPORT.TXT and BOOT.TXT log each start.
  • Failure mode: the camera can hang at start-up. The recovery is to pull the battery and start without the card (resources/RECOVERY.md). That is a much better position than a bad flash, where we found no recovery path except the Update start-up mode.
  • The SD-script setting stays on until a second Mode Set Command turns it off.

4. GR III 2.10, GR IIIx 1.60 and 1.70

We fetched gr3_v210.zip and gr3x_v170.zip from Ricoh with tools/fetch_firmware.py, decoded them with tools/gr_unpack.py, and compared the images word by word (Read).

ComparisonResult
GR III 2.10 vs GR IIIx 1.60, whole decoded image (59,718,388 bytes each) 45 differing words. Model string ("GR III" vs "GR IIIx"), version and build date (0x5300200c to 0x53002078), two instructions at 0x536b62ec and 0x536b6574 (a year constant, 0x7e2 vs 0x7e4, Inferred), a small table of returned constants at 0x5381fe4c–0x5381fe9c (product IDs, Inferred), and the same identity words in the data section.
AF code 0x533e0000–0x53440000 0 differing words
GR IIIx 1.70 vs 1.60, GRKit-style windows of the sites in §5–6 Each window found once. The contrast AF code moved by +0xf0 (search entry 0x53404b24 → 0x53404c14). The shell handlers did not move. The SHELLCMD table has the same 584 entries.

So the GR IIIx is a GR III with a different lens and model ID (the lens data must be selected at run time). Every address in our AF documents is also a valid GRKit gr3-2.10 address. Our hook sites would relocate to 1.70 the way GRKit's do.

A correction to a spot check I made during the survey: only 44 of GRKit's 80 gr3-2.10 addresses are function prologues. That is because many of them are hook sites inside functions or leaf getters, not because the addresses differ.

5. AF debug logging through the engineering shell

The SHELLCMD block (firmware-mod-feasibility) is a table of 584 engineering commands as "name , handler" text. The GRKit loader reaches this shell with sendln. Several entries are AF tools.

5.1 EnableAfDebugDataSave

Handler 0x53017778 (SHELLCMD entry, Read). Usage string "EnableAfDebugDataSave <0/1> [P/C/Z/O]".

  • It gets the AF debug object (singleton 0x5506b56c via 0x533ee89c; constructor 0x533ee7b0 clears it). It parses the first argument as on/off. With no second argument it sets four byte flags at once (0x533efa40). With letters it sets only the named ones: P +0x27, C +0x28, Z +0x29, O +0x2a. It prints "[AF] Debug Data Save P:%d C:%d Z:%d O:%d" (Read).
  • Z is also pushed to the phase AF object (singleton 0x5341df74, [+0x220] byte +0x65, event 0x8000 via 0x534266f4). With it set, 0x53426ba4 takes 0x5341b794, which opens a 10 MB log named "Zaf_DebugLog" (Read).
  • C is tested at the start of the contrast AF logger 0x53407c60 (ldrb [r5,#0x28], with r5 = [obj+0x50]; that this is the debug object is Inferred). The logger opens a 10,000,000-byte log (0x533ef614), writes labelled columns (0x533ef8b8, 0x533ef9a0), and calls the CSV writer 0x533efbd0. Columns (Read, from the label strings): [LensPosition[mm]], [LensPosition[pulse]], [ZafSearchDirection/NOP:0/Far:1/Near:2], [ZafSearchDirectionAreaNo.], [ZafDefocusUm], [ZafPeakAroundCheckAreaNo.], [ZafPeakAroundLooseDecisionGradeFlag], [ZafContrastAfSearchPathDetectPeak], an [-----Algorithm-----] block ([Point] [MaxCounter] [Pulse] [Threshold*1000000] [MaxMinOffset] … [LinearSlope], horizontal and vertical), [AF_Area_Num], [LensPulsePosition] and per area [%d:ContrastAfDataH] [%d:ContrastAfDataV] [%d:YData].
  • File name (Read, 2026-10-29): the CSV writer 0x533efbd0(obj, slot) builds "C:\" + name + "Tmp" + NNNN + ".csv". NNNN is a four-digit counter at 0x5506b568 (padded with "000"/"00"/"0", stops at 9999), shared by all logs. The name of the contrast log is the global string at 0x5506c908, which the start-up code 0x5340ac78 sets to "Caf_Debug". The phase log is named "Zaf_DebugLog". So the files are C:\Caf_DebugTmp0000.csv, C:\Zaf_DebugLogTmp0001.csv and so on, in the card root (C: is the card; GRKit's scripts use C:\SCRIPT\…). The write goes through the updater's file functions (0x53627bdc, then 0x5362eb24).
  • Counter reset: 0x5506b568 lies beyond the initialised data (which ends at 0x5503a080), so it is zero after each power-on. A second session probably overwrites the first session's files (Inferred). Copy the files off the card between sessions.
  • Memory: opening a log (0x533ef614) takes one of 10 slots (+0x112c, 0x14 bytes each) and a buffer of the requested size (10,000,000 bytes for the contrast log, 0xa00000 for the phase log) from a memory pool. If the pool has no more free space than that, it returns 0xff and the logger skips silently (Read). An empty card after a test can mean exactly this.
  • When it is written (corrected 2026-10-29): the labelled-column logger 0x53407c5c is called from 0x53408870 (at 0x5340899c). That function is called from 0x5340aa8c, inside slot 5 (0x5340a80c) of the contrast AF class vtable 0x53c16580. Slot 5 first clears the run flags +0xc45c…+0xc467, so it looks like the start of an AF operation. The previous run's data is then probably written when the next AF starts, which adds card I/O to that start (Inferred). 0x53407b1c, which I named as the caller before, feeds the second writer 0x533f0198 instead.
  • The flags live in RAM and the constructor clears them, so they reset at power-off (Inferred).

What it would give us: for every AF run, the number of contrast samples, the lens pulse of each, the phase defocus, the search direction and the "loose decision" grade flag. That covers the open questions in caf-search-state-machine §6 (the minimum frame count, what 0x5340bc4c really tests) and the sample count part of the 240 fps protocol in af-subsystem §10.6. It does not give wall-clock time unless the CSV has a time column, which the labels do not show. Writing a large CSV to the card may also slow the next AF run, so use sample counts rather than timings from logged runs.

How it would be sent: a card script with sendln 'EnableAfDebugDataSave 1 C' (or CZ), the same way GRKit sends lcmd. That needs SD scripts on, but not GRKit itself and no code patch.

Correction from the camera (2026-10-29, af-debug-log check 3): the C flag alone writes nothing. The contrast logger also needs CAF_Debug SaveDebugFile on, which arms one dump at the next AF start and is cleared after it. sendln reaching the shell is now measured: the C flag read back as 1 from RAM.

Does sendln reach every shell command? In the interpreter, sendln becomes command ID 0x4e (0x538c38b4, Read). I did not trace its executor. The evidence is Structural: GRKit's loader, which works on cameras, sends two different SHELLCMD entries this way (lcmd_resp on, lcmd sh …), and SHELLCMD is one generic "name , handler" table. So any entry is very probably reachable (Inferred). Still open: whether the logger's file writes are safe from the AF task while shooting.

5.2 CAF_Debug

Handler 0x53017958 (Read). Sub-commands and targets: AllOff 0x53416aa4, InfocusTimeMeasure 0x53416f9c, PintShift 0x53417410, CisDriveModeFix 0x5341768c, YDivCoefMeasure 0x53416fe0, JointQuickReturn 0x53417098, MovieLensDebug 0x534170e0, ContrastH1Data 0x53417128, SaveDebugFile 0x5341716c, TestTrace 0x53417310, then GetKfp and DispCurrentState.

InfocusTimeMeasure sets a byte at contrast AF object +0x16d78 (getter 0x533f3b5c, Read). Three places test it (Read, decoded 2026-10-29). Each one prints a line with the RTOS logger 0x536b82d4 and then goes back to the stock path, so the mode is passive logging. This corrects my first reading, which called it a test mode that changes the search.

TestPrintsThen
0x53400e68 "ZAF_SEARCH_START[%d]:%d(%d)": lens position in pulses (0x533ecaf4, parameter 0x5205), +0xe88, byte +0xc51d back to 0x53400e74
0x53406640 "ZAF[%d] PEAK:%d LOG:%d(%d,%d,%d) AREA:%d/%d GAIN:%3.2f F:%d(AVE:%d) N:%d(AVE:%d) --> OFFSET:%d(FULL:%d AVE:%d LIMIT:%d CORRECTION:%d)" stock path
0x5340a638 "RESULT_FOCUS[%d]:%d:%d(%d):%d": lens position in pulses, [+0x24], search path +0xc4ca, halfword +0xc4b8, +0xc430 back to 0x5340a644

The bracketed number is the lens position, not a frame counter, and none of the formats has a time field. The lines go to the RTOS log, not the card. Whether that log adds a timestamp, and whether a card script can read it, is not decoded. If both are true, the start and result markers would give AF time per run without video.

5.3 Other AF shell commands

From the SHELLCMD table (Read; behaviour not decoded): EnableAfBVC, TestAfError, camctl_af, camctl_get_focus_state, the lens commands focus_pi, focus_req, focus_loop, focus_inf, focus_set, focus_rom, focus_vol, focus_spd, focus_tmp, focus_bk, AF_drive, AF_hp, and Af_Led_On/Off. Strings such as m_eContrastAfStopMode and [ContrastAfSearchPath] are printf formats in debug dumps, not commands.

6. Lever 1 as a GRKit hook

Lever 1 (af-subsystem §10.5) is a shorter confirmation after a good phase result. The state machine (caf-search-state-machine) accepts a result when 0x5340bc4c returns 0. Candidate sites, written as GRKit sites. The windows were checked with GRKit's mask and uniqueness rule against GR IIIx 1.60, GR III 2.10 and GR IIIx 1.70 (Read):

Shape of the hook (design, not built). Replace the two BLs with BLs to a runtime function af_peak_check(area, n). When a new capability word CORE.AF_CONFIRM is 0, it tail-calls 0x5340bc4c, so the camera runs stock code. When it is 1, it applies the shorter criterion. The function runs in the AF task once per frame. It may only read the capability word and the AF objects. It may not call UI services or allocate memory. A module AF supplies the on/off page.

What blocks the criterion itself: we still do not know why 0x5340bc4c returning 0 means success (caf §4), or which field holds the phase grade at that moment. The debug CSV (§5.1), with its per-sample data and LooseDecisionGradeFlag column, should answer both, so measurement comes before the hook.

7. Recipes: UserData Set on the GR IIIx

  • SHELLCMD UserData → 0x53008038 (Read). This is the same address the GR IV 1.11 report gives. With four arguments and argv[1] = "Set" it calls the parser 0x5334688c. With three and "Get" it calls 0x53386230.
  • The parser compares argv[2] with each setting name in a long chain (it runs to about 0x53351af0). One example: "StillImageControlNo1ParamStandardSaturation" at 0x53347b50. Each match tail-calls a per-setting function, for example 0x532f2ccc, which matches the value text M4 … M1 … (Read).
  • Names present (Read): 103 StillImageControlNo1… and 103 StillImageControlNo2… (Custom 1 and 2; no No3 on the IIIx), StillActiveImageControlSet, StillWhiteBalance…AdjustBA/GM, StillWhiteBalanceColorTemp, StillHighlightCorrect, StillShadowCorrect, StillLensShadingCorrection, StillHighIsoNR.
  • Missing on the IIIx: camctl_set_user_still_imgctl_custom_name. The recipe name cannot be set on the slot this way.

Consequence: the plan in firmware-mod-feasibility (apply a recipe through 0x53289244, code in the RAW-dev zoom controller, flash) is no longer the best route. Shooting with a recipe needs no code at all: a card script sends the UserData Set lines. Applying a recipe while developing a RAW still needs a hook. GRKit's author plans recipes after an architecture rework (issue #27), so contributing there is better than a separate build.
