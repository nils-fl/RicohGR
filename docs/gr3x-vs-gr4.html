GR IIIx vs GR IV: firmware comparison

Offline comparison of two official firmware packages. Both were downloaded from Ricoh with tools/fetch_firmware.py and decoded with tools/gr_unpack.py. Nothing was run on a camera.

The GR IV file's SHA-256 (a2f664df…655f) and its decoded payload (c4e597c7…33ae) match the sample documented in radium-wang's GR IV repository. The GR IV side of this comparison therefore describes the same binary that project analysed.

Evidence labels match af-subsystem:

  • Read means taken from the data or code directly.
  • Inferred means interpreted.

1. Container format: identical (Read)

  • Both files have the same 0x80-byte header: model string at 0x08, and a four-part version at 0x38.
  • Both use the same frame/LZ compression, as documented by yeahnope/gr_unpack for the GR III.
  • Both carry a whole-file additive checksum.
  • One decoder handles both unchanged.

1.1 GR Mod's container code on the GR IIIx file (Read)

Maxwooow/Ricoh-GRMod (GR IV 1.11 only at the time of this test) has a TypeScript container codec and a self-check. Its three base files (core/src/fw/container.ts, selfcheck.ts, types.ts, commit 675ba64) were run unchanged on both official files. The test ran on 2026-10-15, offline. The test files were deleted afterwards and nothing was flashed. The test edit was +1 / −1 on two adjacent RTOS words at 0x53188900, so the payload and section sums stay zero.

  • The one difference: the GR IV file has 3 model records of 0x80 bytes between the stream and the footer (one per variant). The GR IIIx file has none: the footer follows directly after the padding. selfCheck requires at least one record. If zero records are allowed when the official file has zero, every check passes on the GR IIIx. That change was made only in a scratch copy.
  • Frame layout: GR IV has one 0x8000 frame, 2,763 × 0x6000 and a last partial frame, with 308 stored. GR IIIx has one 0x8000 frame, 2,428 × 0x6000 and a last partial frame, with 729 stored. All stored frames in both files are full 0x6000 frames (prefix E0 00), the only form GR Mod writes.
  • For the test edit, GR Mod stored 1 frame (it re-decodes to find frames whose back-references reach the change). tools/gr_repack.py (the earlier version, before 2026-10-15) stored 2 frames, of 0x7FFF and 0x4001 bytes, because it marks the whole 8 KB back-reference window. Both outputs pass both tools' updater checks and decode to the same payload. GR Mod's self-check rejected ours (frame_layout_unchanged, frames_identical_or_stored_full): frame sizes that do not occur in any official file. That layout is not known to be unsafe, but GR Mod's is the more conservative one. gr_repack.py now keeps the official layout the same way and gives a byte-identical file (firmware-mod-feasibility §4.2).
  • For a port, the container layer carries over with the one-line model-record change. profile.ts (section offsets, GR IV addresses, hashes) and every feature module do not carry over.

Update 2026-10-29. GR Mod 0.8.5 (merged 2026-10-26 from PR #3) supports GR III 2.10 and GR IIIx 1.60 itself, with its own guarded GR IIIx code path. The port notes in this section and in §3.1 are therefore only background. GR Mod does not support GR IIIx 1.70. For the alternative that needs no flash, see gr-mod-landscape.

2. Platform (Read, from each firmware's device tree)

GR IIIx GR IV
Device-tree model Socionext SC2000A EVB w/ RTOS and NETSEC same
CPU listed for Linux one Cortex-A7 (cpu@3) same
Linux memory one region: 0x40000000, 191 MiB two regions: 48 + 112 MiB, plus a 31 MiB RAM block device (slram) between them
Linux root file system eMMC partition (root=/dev/mmcblk0p2); gzip-compressed cpio initramfs in the payload RAM-backed MTD (root=/dev/mtdblock0, slram); the payload uses xz/squashfs-style packing
Kernel log level loglevel=4 loglevel=0

Both cameras use the same SoC (Milbeaut M10V / SC2000A) and the same two-OS split. A real-time OS on the image side runs capture, AF, AE and UI. Linux on one A7 core handles Wi-Fi, Bluetooth and USB. The notable change is where Linux boots from:

  • the GR IIIx mounts its root file system from eMMC;
  • the GR IV unpacks it into a 31 MiB RAM disk, which costs Linux about 31 MiB of its address map (160 MiB usable, compared with 191 MiB).

The GR IV repository reports 2 GiB of physical LPDDR3 from a teardown. Neither device tree shows how the rest of physical memory is split between the domains.

3.1 GR Mod profile values for the GR IIIx (Read unless marked)

These are the GR IIIx counterparts of what GR Mod's core/src/fw/profile.ts holds for the GR IV: hashes, section places and the image-control tables its slot editor uses. They were found offline on 2026-10-15. A draft profile with these values passes its own asserts on the official 1.60 file. It is kept outside this repository, because GR Mod is GPL-2.0-only. Superseded on 2026-10-26: GR Mod 0.8.5 supports the GR IIIx 1.60 natively (§1.1).

  • How the tables were found. The GR IIIx parameter builder 0x536dc0f4 is the counterpart of the GR IV's 0x53912c40. Both store the style record at [r4+8], the multi-axis record at [r4+0xc] and a third table at [r4+0x18] (GR IIIx 0x55018e4c, GR IV 0x55052cf4). The GR IV fetches each through a getter that computes table[variant × 34 + style] after a style remap table. The GR IIIx indexes the tables with the image-control byte [r7+0x77c] directly, reading 0x16 as 0x19.
  • Same record layout. Words 0–11 of every style record have the same roles on both cameras. Word 1 is the 3×3 Q13 colour matrix, and word 2 is the 9-pointer post-curve array whose entry 4 is the identity.
  • Style numbers (Inferred). 0x0b is Standard: its record also sits at 0x14 and 0x15, just as the GR IV's Standard record sits at 0x0b, 0x16 and 0x17. The enum that maps the 12 image controls to the 26 entries has not been read.
  • Tone curves (Read, except where marked). Where the GR IV stores T_GAM[style] ([r4+0x14]; descriptor layout: parameter block, flags, then R/G/B curves at +8/+0xc/+0x10), the GR IIIx builder stores one constant for every style: 0x53dd9d84, the only value it ever stores there. Its first word, 0x53dd1b78, is a parameter block of the same kind as the GR IV descriptors' first word (it starts with the same 01 00 01 01 01 header). The words after that differ: 0x550204b0, 0x550204b0, 0x550204fc, 0, 0. They are RAM arrays of pointers to a bank of about 21 curves, each 256 × u16 rising to about 16,290 (0x53dcf5f0–0x53ddd65c). Code in src/R2Y/ToneControlTuning.cpp (0x536e82d0, using the 7-entry array at 0x550204e0) picks two neighbouring bank curves and interpolates between them, so the GR IIIx builds its tone curve at run time instead of reading a fixed per-style curve. 15 of the bank curves also exist in the GR IV, in the region its own descriptor curves use. The GR IV's per-style R/G/B curves (Standard, Cinema (Green), the monochrome one) do not occur in the GR IIIx. The GR IV is not far from this either: its 34 styles share only 4 descriptors.
    The reader (Read). The per-channel tone step is the same function on both cameras, found through identical callers (GR IV 0x5391ec98, GR IIIx 0x536e8fc0, both 0x40 bytes, which call it second): GR IV 0x5391e340, GR IIIx 0x536e8660. Both first test byte [r1+0x9b]. That flag is set by GR IV 0x53910d34 / GR IIIx 0x536db130 when a settings byte ([[+0x2d0]+0x38ad0] on the GR IV, +0x38a98 on the GR IIIx) is non-zero. Values 1–11 map through [8, 0, 1, …, 10] (GR IIIx 0x53dbd19c).
    • Flag set (both cameras): a getter (GR IV 0x53925000, GR IIIx 0x536eedf0) takes three index bytes (+0xe/+0xf/+0x10 of a state object) into a 12-curve table: GR IV 0x55052c64, GR IIIx 0x55037604. The two tables are the same curves, entry for entry (same ranges and the same number of dips per curve). The step then maps the base curve through the R, G and B curves; the blend weights are 77/150/29.
    • Flag clear, GR IV only: the reader loads the per-style descriptor from [r1+0x14]. If its byte +4 is set (Cinema (Yellow): flags 0x101), it uses the descriptor's R/G/B curves at +8/+0xc/+0x10. Otherwise (Standard: 0) it takes the default path.
    • Flag clear, GR IIIx: there is no descriptor branch. The function never reads [r1+0x14], and the default path copies the same curve into all channels.
    The settings byte is Cross Process (Read). It is not a menu setting. It is a working value, and its only writer is GR IIIx 0x536dd270 (GR IV 0x53912990). That writer stores 0 unless the image control (+0x77c) is 0x15 (GR IV 0x17). For 0x15 it stores 2, 3 or 4 for the Cross Process toning value 0, 1 or 2 (+0x797; GR IV +0x7b9), and 0 for any other value. The byte at +0x797 is Cross Process toning:
    • the Cross Process toning getter 0x5328410c (slot 11 in the feasibility doc's §4.4) returns it;
    • its setter 0x53559904 has the same form as the image-control setter 0x53558260;
    • its formatter 0x532acf54 accepts only 0, 1 and 2, labelled "B", "M" and "Y" (Basic, Magenta, Yellow; Inferred names) and asserts on anything else.
    Through 0x53dbd19c, 2/3/4 select curve sets 1/2/3 of the 12-curve table. So the shared per-channel path is Cross Process's own R/G/B curves, one set per toning, on both cameras. Every other control leaves the flag clear. That also fixes image control 0x15 as Cross Process (Read). The ImageControlModel.cpp lists (0x53b58fcc, 0x53b5919c, 0x53b59224) hold 0x0b–0x10, 0x16, 0x11–0x15. This fits Standard = 0x0b and the eleven older controls numbered in order up to Cross Process = 0x15, with Negative Film added as 0x16 (Inferred; the builder reads 0x16 as entry 0x19).
    For a port: the GR IIIx lacks the GR IV's per-style curve branch, not just its data. Per-slot curves would need a code change in 0x536e8660 (ToneControlTuning.cpp, outside the guard's allow-list) that adds that branch and reads a per-style curve pointer (from a new table, or from the descriptor slot that builder 0x536dc394 fills). The R/G/B blend code that follows can be reused as it is.

4. Where the two firmwares differ by subsystem (Structural)

Source files (src/*.cpp) present in only one image:

Subsystem GR IIIx only GR IV only
AF AeAfLinkData, AfLensDrive, AfLromCommunication, ZafContrast, ZafControl, ZafDefine, ZafFilter, ZafShadingAlgorithm AfCommonFilter, CafProjectDependData
Lens LensInformation, LensVignettingCorrection LensFocusControl, LensState, ShutterControl
AE / AWB AeApertureCorrect, AeChangeData, AeCheckComposition AeFlashAlgorithm
Stabilisation SricCenterDriveControlService SricClient, SricFwUpdate and seven SricM343* files
Communication WlanRfPower, WlanRfTestCommand WlanRegionCodeInfo
System / UI none BootOther, MeasurementController

What stands out:

  • Stabilisation is the largest hardware change. The GR IV image carries a full SricM343* client stack: gyro and accelerometer requests, LPF and filter data, firmware update, memory read/write and boot commands. The class count for the subsystem goes from 44 to 114. The GR IIIx has no such stack. Read as Inferred: the GR IV talks to a separate stabilisation controller over a command protocol.
  • The AF code is mostly the same, with targeted changes. The GR IV image keeps every Zaf* and Caf* class that the algorithm needs. The names missing from it (ZafPixelInfo, ZafSensorInfo, ZafPulse, ZafShadingAlgorithm, AfLensDrive, AfLensCommunication) do not mean the algorithm is gone. §5 compares the code at address level.
  • AF log strings match. Both images have the same 12 AF log strings.
  • Lens and shutter control moved into new classes on the GR IV (LensState, LensFocusControl, ShutterControl), while the GR IIIx has LensFmmCalc, LensInformation and LensLromData. The GR IIIx AF document's lens-calibration path (AfLromCommunication, CafIndividualLensCorrect, see §3.8b) therefore may not carry over to the GR IV unchanged.
  • UI grew (about 286 to 312 classes) with user-mode box, outdoor monitor, mobile-app guide and measurement controllers.
  • The Wi-Fi RF test code differs (WlanRfPower, WlanRfTestCommand only on the GR IIIx; WlanRegionCode* only on the GR IV).

5. AF at address level (Read, unless marked)

Method. Both RTOS images were disassembled with Capstone. Every function was fingerprinted by its instruction sequence with addresses removed. The 75 functions that af-subsystem cites by address were then matched to the GR IV image, and their instruction sequences and immediate constants were compared by hand where they differed. Load tools/rtos_analysis.py with GR_FW=work/fwdc248b-v111.decoded.bin and set OFF = 0x17D10 to read the GR IV image with the same helpers.

Function addresses are GR IIIx → GR IV.

5.2 Same algorithm, small change

  • Peak fit (CalcQuadraticCurve, 4.2, 0x5340ed10 → 0x53605668). The three-point parabola uses the same floating-point operations. The GR IIIx converts the result to an integer (vcvt.u32.f64) before returning it. The GR IV returns the double unrounded. I did not trace what the callers do with the extra precision.
  • Phase result used by contrast AF (5.4, 0x533fed24 → 0x535f7550). The reliability ≤ 128 test is still there (cmp #0x80 on the block record). The per-block record stride goes from 7 to 9 (Inferred: two more bytes of per-block data).
  • Wobble history evaluation (0x53413588 → 0x53609660) grows from 1,138 to 1,442 instructions. The old thresholds are still present. About 50 new constants are added (values such as 120, 15, 14 and 13), so this function gained logic. I did not decode it.

5.3 Phase detection: what changed

Correlation metric. The NEON kernels use the same vabd.u16 / vpadal (SAD) and vmlal (SSD) pattern with a lane-mask tail. The GR IIIx has four kernels (0x533e807c, 0x533e8130, 0x533e8234, 0x533e8304). The GR IV has three (0x535e6328, 0x535e63f4, 0x535e6504), and its first kernel uses a fixed one-sample offset (add r0, r3, #2) where the GR IIIx takes it as a parameter.

Pre-filter. This changed most.

  • The GR IIIx has four levels (spacing 2^k, k = 0…3) of both the [1 2 1] smoothing and the [1 0 −1] difference kernel, plus a dispatcher that picks the level (0x5341c884). The higher levels use vld2/vld4 loads.
  • The GR IV has no vld4.16 in the AF code and no level query. The difference kernel (0x535e6d24, y = x + 0x8000 − x[i+2s]) is one generic routine, and its dispatcher (0x53612830) calls it with fixed arguments. A single vhadd smoothing kernel remains (0x535e6bbc).
  • In the GR IIIx 1.60 the level function (0x5341c884) always returns 0, so only the level-0 kernels ever run there too. The GR IV removed dead code; it did not lose a working feature (Read).

Reliability grading. The GR IIIx compares fixed limits in code (64, 15, 128, 192, 216, 256, 11; §3.8). In the GR IV, 0x5360f894 computes the same two quantities and compares them with values read from tables (0x53eaa840 and 0x53eaba58, indexed by a mode byte):

  • The error limit is 64 and the valley-depth limit is 16 (a depth of 15 or less is shallow). Both equal the GR IIIx values for the first four table entries.
  • The relaxed limits 128, 192, 216 and 256 and the near-focus exception (|shift| ≤ 11) do not appear as constants anywhere in the GR IV AF code. If they exist, they now live in data. The table entries after the fourth are other data and were not interpreted.
  • The error term is computed differently: max(0, S₀ − |S₊ − S₋| / 2), where S₀, S₋ and S₊ are the SAD values at and beside the minimum. The GR IIIx uses SADmin − H0 with the noise floor H0 of §3.7. The GR IV has no CalcH0 string or function. The depth is SADneighbour − S₀, with no H0. Reading this as a V-shape residual is Inferred.
  • The candidate-selection cross-multiplication (SAD₁·C₂ vs SAD₂·C₁) is still present (0x5360f98c).

New phase-detection features (Structural). The GR IV ZafOperationAccessor has backup fields with no GR IIIx counterpart: ZafDeadZoneCorr* (Exe, Defocus, DefocusBeforeUpdate, PredictorOk, ReliabilityData, BottomLinearNg), ZafSaturation, ZafDefect, FakeBottomDoubt, BottomLinearNg, BottomLinearShiftZero, Gradation, DifferentialFilterExe, WaveLevelGapCorrectExe, NormalContrastOk and FinalContrastOk. From the names, the GR IV detects saturated pixels, treats a "fake" or linear-bottom SAD minimum as doubtful, and has a dead-zone correction of the defocus. No call site for these setters was found by a static scan, so where they are set is not known. The per-block summary flag word (0x53613d3c) combines 16 boolean getters, against 20 in the GR IIIx (0x5341fea4); the two sets of bits differ.

Shift → defocus (§3.8b). The GR IV keeps the structure K = table[index] × polynomial(x) (0x53614688) but generalises it:

  • a four-entry ring buffer of lens-state snapshots feeds the calculation;
  • parameters are chosen by a lens-type byte, with a coefficient triple per type and bank, and the table is indexed by a bank bit plus the aperture;
  • the aperture index is clamped to 24…64 for types 0–3 (GR IIIx: 24…96);
  • 97-entry tables are used, as in the GR IIIx.

I did not decode what feeds x or the table contents, so the GR IV calibration values are not compared with the GR IIIx ones.

5.4 Not compared

The ISO-dependent AF filter strength (4.6), the scan stepping (4.7), the continuous-AF re-trigger (5.6, 0x53405e8c → 0x53601914, a similar but modified function) and the motor parameters were not compared in detail.
